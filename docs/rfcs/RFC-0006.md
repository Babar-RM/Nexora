# RFC-0006: Three-Address Code (IR)

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-28
- **Depends on:** RFC-0002, RFC-0003, RFC-0005
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines Nexora's intermediate representation: **Three-Address Code (TAC)** in quadruple form. It specifies the operand and instruction set, the textual and JSON formats, how every AST construct is lowered (including short-circuit logic, loops, and calls), the basic-block and control-flow-graph (CFG) structure, a validator, and a small TAC interpreter used for testing.

## 2. Motivation

The AST is shaped like the source language. TAC is shaped like a simple machine: every instruction has at most one operator and at most three operands. That makes it:

1. the standard place to demonstrate **classical compiler theory** (basic blocks, CFG, data-flow style optimizations — RFC-0007);
2. a **language-independent** middle layer, separating MiniLang analysis from target generation (RFC-0002 §3.3);
3. something the **frontend can visualize** to teach how an expression like `a + b * 2` is evaluated step by step.

In v1, the Python generator reads the AST, not TAC (RFC-0002 §3.3). TAC is nevertheless a first-class, tested phase output and the foundation for future low-level targets.

## 3. Detailed design

### 3.1 Operands

```python
@dataclass(frozen=True)
class Const:     value: int | float | str | bool; type: Type
@dataclass(frozen=True)
class Var:       name: str; type: Type        # a MiniLang variable or parameter
@dataclass(frozen=True)
class Temp:      name: str; type: Type        # compiler temporary: t1, t2, ...

Operand = Const | Var | Temp
```

- Temps are numbered `t1, t2, …` and labels `L1, L2, …` by a counter owned by the `IRGenerator` instance, starting at 1 for every compilation (RFC-0002 §3.4 Phase 4).
- `Temp` and `Var` are distinct classes, so a user variable named `t1` never collides with a temporary; the textual form is for display only.
- Every operand carries its static `Type` (from semantic analysis). This lets future targets generate typed code.

### 3.2 Instruction set

All instructions are frozen dataclasses with a `source_line: int` (the MiniLang line that produced them; 0 if synthetic).

| Instruction | Fields | Text form | Meaning |
|---|---|---|---|
| `Copy` | `dest, src` | `x = y` | assign |
| `BinOp` | `dest, op, left, right` | `t1 = a + b` | binary operation |
| `UnOp` | `dest, op, operand` | `t1 = - a`, `t1 = not a`, `t1 = float a` | unary op (`neg`, `not`) or widening conversion (`float`) |
| `Label` | `name` | `L1:` | jump target |
| `Goto` | `target` | `goto L1` | unconditional jump |
| `IfFalse` | `cond, target` | `ifFalse t1 goto L1` | jump when `cond` is false |
| `IfTrue` | `cond, target` | `ifTrue t1 goto L1` | jump when `cond` is true |
| `Param` | `arg` | `param t2` | push an argument for the next call |
| `Call` | `dest \| None, func, argc` | `t3 = call f, 2` / `call f, 0` | call; consumes the preceding `argc` params |
| `Return` | `value \| None` | `return t4` / `return` | leave the function (lowering of `give`) |
| `Print` | `value` | `print t5` | implements `show` (bool printed as `true`/`false`) |
| `Ask` | `dest, type` | `x = ask int` | read from stdin with type (`int`, `float`, `string`) |
| `FuncBegin` | `name, params, ret` | `func f(a, b):` | start of function / task |
| `FuncEnd` | `name` | `endfunc` | end of function / task |

Binary `op` ∈ `+ - * / % == != < <= > >=`. Logical `both`/`either` and `not` on **control flow** are lowered as described in §3.4; the instruction set has no `both`/`either` operator. `UnOp` `not` exists for value negation.

**Semantics notes**

- `/` always produces `float`; `%` and the other arithmetic ops follow RFC-0001 §3.6. Division/modulo by zero is a **runtime error** at that instruction.
- `Print` of a `bool` shows `true`/`false`; of a `float` shows the shortest round-trip form (RFC-0001 §3.5).
- `Param`s are consumed in order by the next `Call`. Calls never interleave their params (see §3.4, calls).
- Variables are function-local (parameters and `make`s inside the task) or global (`make` at top level, in `__main`). Functions only read globals (RFC-0001 §3.4), so a `Call` can never modify a variable of the caller.

### 3.3 Program layout

The IR generator returns a **flat `list[TACInstr]`** (as fixed in RFC-0002):

```
func factorial(n):
  ...
endfunc
func __main():
  ...
endfunc
```

- User functions appear in source order, followed by one synthetic `func __main():` containing all top-level statements in source order.
- Every function ends with a `Return`: if the source function is void, an implicit `return` is appended; if it is non-void, a final value-less `return` is appended and is provably unreachable (semantic analysis guarantees all paths return). The optimizer removes it (RFC-0007).
- Parameters of `FuncBegin` are `(name, Type)` pairs.

### 3.4 Lowering rules (AST → TAC)

Notation: `gen(e)` returns an operand holding the value of expression `e` after emitting instructions for it. `new_temp()` and `new_label()` use the generator's counters.

**Expressions**

| AST | Lowering |
|---|---|
| literal | `Const(value, type)` (no instruction) |
| `Identifier x` | `Var(x)` (no instruction) |
| `UnaryExpr(-, e)` | `a = gen(e)`; `t = - a` |
| `UnaryExpr(not, e)` | `a = gen(e)`; `t = not a` |
| `BinaryExpr(op, l, r)` (arithmetic/comparison) | `a = gen(l)`; `b = gen(r)`; `t = a op b` |
| `BinaryExpr(both, l, r)` | short-circuit, see below |
| `BinaryExpr(either, l, r)` | short-circuit, see below |
| `CallExpr(f, args)` | evaluate **all** args to operands left to right; then one `param` per arg in order; then `t = call f, n` (or `call f, n` if the result type is `void`) |

Widening (`needs_widening` / `arg_widenings` from RFC-0005): after generating the operand `a` that will be assigned/passed/returned into a `float` slot, emit `t = float a` and use `t` instead. Literal `Const` operands are converted at generation time (`Const(2.0, FLOAT)`).

**Short-circuit `both`** (result temp `t`; the temp is assigned on two paths):

```
a = gen(l)
t = a
ifFalse t goto Lend
b = gen(r)
t = b
Lend:
```

**Short-circuit `either`:**

```
a = gen(l)
t = a
ifTrue t goto Lend
b = gen(r)
t = b
Lend:
```

The right operand's instructions appear only on the path where it is evaluated, preserving MiniLang's short-circuit semantics (and its runtime errors).

**Statements**

| AST | Lowering |
|---|---|
| `MakeStmt x: T = e` | `v = gen(e)`; `x = v` (as `Copy`) — if `v` is a fresh temp from the last instruction, the generator MAY retarget that instruction's `dest` to `x` and skip the `Copy` (a mandatory peephole so output is readable) |
| `AssignStmt` | same as `MakeStmt` |
| `ShowStmt e` | `v = gen(e)`; `print v` |
| `AskStmt x: T` | `x = ask T` |
| `ExprStmt e` | `gen(e)` (a bare `call` if void; otherwise the value is discarded) |
| `GiveStmt e` | `v = gen(e)`; `return v` / `return` |
| `Block` | lower children in order |
| `WhenStmt` without otherwise | `c = gen(cond)`; `ifFalse c goto Lend`; then-block; `Lend:` |
| `WhenStmt` with otherwise | `c = gen(cond)`; `ifFalse c goto Lelse`; then-block; `goto Lend`; `Lelse:`; else-branch; `Lend:` |
| `otherwise when` | the else branch is a `WhenStmt`, lowered recursively |
| `DuringStmt` | `Lstart:`; `c = gen(cond)`; `ifFalse c goto Lend`; body; `goto Lstart`; `Lend:` |
| `StopStmt` | `goto Lend` (target is the end label of innermost enclosing `during` loop) |
| `SkipStmt` | `goto Lstart` (target is the start label of innermost enclosing `during` loop) |

Labels are allocated before lowering the parts that jump to them; numbering is therefore deterministic (outer constructs get lower numbers).

### 3.5 Worked examples

**Example A — expression**

```
make result = 2 + 3 * 4;
show(result);
```

```
func __main():
  t1 = 3 * 4
  t2 = 2 + t1
  result = t2
  print result
  return
endfunc
```

**Example B — task with recursion**

```
task factorial(n: int): int {
    when (n <= 1) { give 1; }
    give n * factorial(n - 1);
}
make i = 1;
during (i <= 5) { show(factorial(i)); i = i + 1; }
```

```
func factorial(n):
  t1 = n <= 1
  ifFalse t1 goto L1
  return 1
L1:
  t2 = n - 1
  param t2
  t3 = call factorial, 1
  t4 = n * t3
  return t4
  return
endfunc
func __main():
  i = 1
L2:
  t5 = i <= 5
  ifFalse t5 goto L3
  param i
  t6 = call factorial, 1
  print t6
  i = i + 1
  goto L2
L3:
  return
endfunc
```

Note `i = i + 1`: the retarget peephole of §3.4 rewrites `t7 = i + 1; i = t7` into one instruction, so no temp is consumed.

**Example C — short-circuit**

```
make ok = a > 0 both b / a > 2;
```

```
  t1 = a > 0
  t2 = t1
  ifFalse t2 goto L1
  t3 = b / a
  t4 = t3 > 2
  t2 = t4
L1:
  ok = t2
```

`b / a` is evaluated only when `a > 0`, so there is no division by zero when `a == 0`.

### 3.6 Basic blocks and the CFG

```python
@dataclass
class BasicBlock:
    id: int                      # B0, B1, ... per function
    label: str | None            # the Label that starts it, if any
    instrs: list[TACInstr]       # without FuncBegin/FuncEnd
    succ: list[int]              # ids of successor blocks
    pred: list[int]

@dataclass
class CFG:
    function: str
    blocks: list[BasicBlock]
    entry: int                   # always 0
```

**Leaders** (first instruction of a block):

1. the first instruction after `FuncBegin`;
2. every `Label` instruction;
3. every instruction immediately after a `Goto`, `IfFalse`, `IfTrue`, or `Return`.

A block extends from a leader up to (not including) the next leader. **Edges:**

- block ending in `Goto L` → block starting at `L`;
- block ending in `IfFalse`/`IfTrue` → the target block **and** the fall-through block;
- block ending in `Return` → no successors;
- any other block → the fall-through block.

Functions: `build_cfg(function_instrs) -> CFG`, `build_all_cfgs(tac) -> list[CFG]`, and `flatten_cfg(cfg) -> list[TACInstr]` (blocks emitted in id order; used by the optimizer after rewriting). The CFG JSON (`blocks` with `succ`) is exposed to the frontend for a graph view.

### 3.7 Formats

**Text** (`format_tac(instrs) -> list[str]`): exactly the forms in §3.2, indented two spaces inside functions, labels at column 0. Constants render as: ints as digits, floats via `repr`, strings JSON-quoted, bools `true`/`false`.

**JSON** per instruction:

```json
{ "op": "binop", "dest": "t1", "operator": "*", "left": "3", "right": "4",
  "type": "int", "text": "t1 = 3 * 4", "line": 1 }
```

`op` ∈ `copy | binop | unop | label | goto | iffalse | iftrue | param | call | return | print | ask | func | endfunc`. `text` is the display string; `line` is the MiniLang source line (0 for synthetic).

### 3.8 Validator

`validate_tac(instrs)` raises `InternalCompilerError` on a violation. Invariants:

1. `FuncBegin`/`FuncEnd` are properly paired and not nested; every non-function instruction is inside a function.
2. Every `Goto`/`IfFalse`/`IfTrue` target label is defined exactly once in the same function; labels are unique per function.
3. Every `Temp` is **defined before use on the textual path** of its function (temps are assigned by exactly one instruction, except the two-assignment short-circuit pattern of §3.4).
4. Each `Call` is preceded by exactly `argc` `Param`s that belong to it (no foreign instruction other than `Param` between the first of them and the call).
5. Every function's last instruction before `FuncEnd` is a `Return`.
6. Operand types are consistent with the opcode (e.g. `ifFalse` condition is `bool`).

The pipeline calls the validator after IR generation **and after every optimizer pass** in test/debug mode (`NEXORA_VALIDATE_IR=1`; always on in the test suite).

### 3.9 TAC interpreter (test utility)

`tests/helpers/tac_vm.py` executes a TAC list and returns stdout text and an optional runtime error code. It is **not** part of the shipped compiler. Purpose: *differential testing* — for every example program, `run(tac) == run(python)` (same stdout, same runtime error), and `run(optimized_tac) == run(tac)`. This proves the IR generator and the TAC optimizer preserve semantics independently of the Python generator.

Semantics of the VM: a call stack of frames (`dict[str, value]`), a param stack, labels resolved to indices, Python `int`/`float`/`str`/`bool` for values, `print` using the bool/`float` formatting of RFC-0001. Globals live in the `__main` frame and are readable by functions by name (matching RFC-0001 §3.4 rule 7).

### 3.10 Module layout

`ir.py` contains operands, instruction classes, `IRGenerator(NodeVisitor)`, `format_tac`, `tac_to_dict`, `build_cfg`, `flatten_cfg`, and `validate_tac`. It imports only from `errors`, `ast_nodes`, `symbols` (one-way rule).

## 4. Alternatives considered

1. **Triples / indirect triples** (instructions refer to other instructions by index). More compact, but harder to read and to rewrite during optimization. Quadruples with named temps are clearer for a teaching/visualization project.
2. **SSA form.** Enables powerful optimizations but adds φ-nodes and construction algorithms — too large for v1. TAC with a clean CFG leaves SSA as a future RFC.
3. **Stack bytecode** (like Python's or the JVM's). Compact and easy to interpret, but it hides the “three addresses” the project aims to demonstrate.
4. **No IR** (AST → Python directly). Rejected: the architecture goals of the project (RFC-0002) require an IR phase.
5. **Lowering `both`/`either` to non-short-circuit operators.** Rejected: it would change semantics (evaluation and runtime errors in the right operand).
6. **Structured IR** (keeping `when`/`during`). Closer to Python output but not a real low-level IR and defeats CFG/optimization demonstrations.

## 5. Drawbacks and risks

- Maintaining two lowerings of the same program (AST → Python and AST → TAC) can drift apart; mitigated by differential tests (§3.9) and by the rule that both consume the same annotated AST.
- The short-circuit temp is assigned twice, so temps are not strictly single-assignment; passes must not assume SSA-like properties.
- Flat instruction lists need the validator to keep label/function structure sound.

## 6. Impact on other components

- **Optimizer (RFC-0007):** TAC-level passes work on the CFG defined here.
- **Pipeline:** produces `tac` (text list) and `cfg` (JSON) in `CompileResult`; RFC-0002 §3.7 gains an optional `cfg` field.
- **Frontend (RFC-0010):** TAC tab (grouped by basic block), CFG diagram, source-line cross-highlighting via `line`.
- **Semantic analyzer:** must set `type`, `needs_widening`, and `arg_widenings` correctly (RFC-0005 §3.7); the IR generator relies on them.

## 7. Test plan

- **Golden lowering tests:** for each construct in §3.4 (expression forms, `make`, assign, `show`, `ask`, `when`, `when/otherwise`, `during`, `give`, `stop`, `skip`, calls with nested calls, widening, short-circuit `both`/`either`) compare `format_tac` output with a stored expected listing.
- **Determinism:** compiling twice yields identical TAC; temp/label numbering starts at 1 each time.
- **Call discipline:** `f(g(1), 2)` produces both inner computations before any outer `param`.
- **CFG tests:** leaders, edges for `when`, `during`, nested loops, early `give`; every block reachable in the unoptimized output except the provably unreachable trailing return.
- **Validator tests:** each invariant has a hand-built bad TAC that triggers `InternalCompilerError`.
- **Differential tests:** every `examples/*.mini`: `tac_vm(tac)` equals the stdout of the generated Python run through the runner.
- **Fixture invariants:** every program in `tests/fixtures/valid/` passes `validate_tac`.

## 8. Open questions

1. Retarget peephole (§3.4 `MakeStmt`) — mandatory or optional? (Proposed: mandatory, so output is stable and readable.)
2. Should `Print` take a type-specific opcode (`printb`, `printf`)? (Proposed: no; operands carry types.)
3. Should the CFG be returned in the main API response or only on request? (Proposed: include; the payload is small.)
4. SSA as a future RFC after RFC-0009? (Proposed: yes, if time allows.)
