# RFC-0002: Compiler Architecture and Phase Contracts

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-21
- **Depends on:** RFC-0001
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines Nexora's overall architecture: the pipeline of phases, the data structure each phase consumes and produces, the invariants each phase guarantees, how phases are wired together, the public API (`pipeline.py` and the HTTP contract), and the decision to generate Python from the AST while producing TAC for analysis and future targets.

## 2. Motivation

Four people build different phases in parallel. They need a shared picture of *what flows between phases* and *who guarantees what*, so that integration is boring. The frontend also needs a stable, inspectable output for every phase.

## 3. Detailed design

### 3.1 Pipeline overview

```
 source: str
    │
    ▼  Phase 1  Lexer                 → list[Token]
    ▼  Phase 2  Parser                → Program (AST)            + syntax diagnostics
    ▼  Phase 3  SemanticAnalyzer      → typed AST + SymbolTable  + semantic diagnostics
    ▼  Phase 4  IRGenerator           → list[TACInstr]
    ▼  Phase 5  Optimizer             → optimized AST  and  optimized list[TACInstr]
    ▼  Phase 6  PythonCodeGenerator   → python: str
    ▼  Phase 7  Runner (optional)     → RunResult(stdout, stderr, exit_code, timed_out)
```

Each arrow is a plain function call on plain data. There are no callbacks, hidden shared state, or global registries.

### 3.2 Components and responsibilities

| # | Component | Module | Input | Output |
|---|---|---|---|---|
| 1 | Lexer | `lexer.py` | `str` | `list[Token]` |
| 2 | Parser | `parser.py` | `list[Token]` | `Program` + diagnostics |
| 3 | Semantic analyzer | `semantic.py`, `symbols.py` | `Program` | annotated `Program`, `SymbolTable`, diagnostics |
| 4 | IR generator | `ir.py` | annotated `Program` | `list[TACInstr]` |
| 5 | Optimizer | `optimizer.py` | `Program`, `list[TACInstr]` | optimized versions of both |
| 6 | Code generator | `codegen_python.py` | optimized `Program` | `str` |
| 7 | Runner | `runner.py` | `str` | `RunResult` |
| — | Pipeline | `pipeline.py` | `str`, options | `CompileResult` |

### 3.3 Why Python is generated from the AST, and what TAC is for

Python has no `goto`. Translating TAC (labels and jumps) back to readable `if`/`while`/`def` requires structure recovery, which is a research-level problem and produces ugly code. The AST already has the structure.

Therefore:

1. **Python code generation consumes the (optimized) AST.** Output is readable and faithful.
2. **TAC is generated from the AST** and is the language-independent IR used for: visualization, TAC-level optimizations (constant propagation, copy propagation, dead-temporary elimination), teaching/demonstration, and as the input for a future *low-level* target or analyses.
3. **Two optimizer levels** (RFC-0007): AST-level (constant folding, constant-condition branch elimination) feeds the code generator; TAC-level (shown in the UI) demonstrates classic IR optimization. Both share one folding rule set so they cannot disagree.
4. Future high-level targets (JavaScript, Java) use the same AST → generator pattern: add `codegen_js.py` implementing the same interface (§3.8).

This is a deliberate trade-off: the project demonstrates every classical phase while keeping output quality high and scope achievable.

### 3.4 Phase contracts (guarantees and invariants)

A phase MAY assume its input satisfies the previous phase's guarantees and MUST establish its own.

**Phase 1 — Lexer**
- Input: any `str`.
- Output: `list[Token]` ending with **exactly one** `EOF` token.
- Every token has `type`, `lexeme`, `value`, 1-based `line` and `column`.
- Comments and whitespace do not appear in the output.
- Fails fast with `LexerError` (E1xxx) on the first invalid input.
- Never raises anything other than `LexerError` for any input (fuzz-testable).

**Phase 2 — Parser**
- Input: token list from Phase 1.
- Output: `Program` AST (RFC-0003) and a list of syntax diagnostics (E2xxx).
- If there are no diagnostics, the AST is **complete and conforms to the RFC-0001 grammar**.
- If there are diagnostics, the AST may be partial and MUST NOT be passed to later phases (the pipeline stops).
- Every node has `line` and `column` of its first token.
- Uses panic-mode recovery (RFC-0004 §5.2) so one run reports multiple independent syntax errors.

**Phase 3 — Semantic analyzer**
- Input: syntactically valid `Program`.
- Output: the same tree, **annotated** (`type` on every expression, `symbol` on every identifier/call), a `SymbolTable` snapshot, and diagnostics (E3xxx, warnings W4xxx).
- If there are no *errors* (warnings are allowed), the program satisfies all rules of RFC-0001 §3.3–3.6; later phases may assume names resolve, types match, and all paths return.
- Collects all errors; does not stop at the first.

**Phase 4 — IR generator**
- Input: semantically valid, annotated `Program`.
- Output: `list[TACInstr]` (RFC-0006). Every instruction has at most one operator; temporaries are named `t1, t2, …` and labels `L1, L2, …`, numbered per compilation starting at 1.
- Cannot fail on valid input (any failure is an `InternalCompilerError`).

**Phase 5 — Optimizer**
- Input: annotated `Program` and its TAC.
- Output: optimized `Program` and optimized TAC.
- MUST preserve observable behaviour exactly: same output, same runtime errors (RFC-0007).
- Idempotent: optimizing an already optimized program changes nothing.

**Phase 6 — Code generator**
- Input: optimized, annotated `Program`.
- Output: Python source `str`; deterministic; runs under Python 3.10+ with the standard library only.
- The output compiles (`ast.parse` succeeds) for every valid input — asserted in tests.

**Phase 7 — Runner**
- Input: Python source `str`, options (timeout, output cap).
- Output: `RunResult`.
- Executes in an isolated subprocess (RFC-0009). Never raises on user-code failure; failures are data in `RunResult`.

### 3.5 Public API of the compiler package

`pipeline.py` is the only entry point used by `main.py`, `api.py`, and integration tests.

```python
from dataclasses import dataclass, field
from .errors import Diagnostic

@dataclass
class CompileOptions:
    run: bool = False              # execute the generated Python
    optimize: bool = True
    target: str = "python"         # future: "javascript", "java"
    timeout_seconds: float = 5.0
    max_source_bytes: int = 64 * 1024

@dataclass
class CompileResult:
    source: str
    tokens: list[dict] | None = None
    ast: dict | None = None
    symbols: list[dict] | None = None
    tac: list[str] | None = None
    optimized_tac: list[str] | None = None
    python: str | None = None
    run: dict | None = None        # stdout, stderr, exit_code, timed_out
    diagnostics: list[Diagnostic] = field(default_factory=list)

    @property
    def ok(self) -> bool:
        return not any(d.severity == "error" for d in self.diagnostics)

def compile_source(source: str, options: CompileOptions | None = None) -> CompileResult: ...
```

**Stop rules** (a failing phase stops the pipeline; earlier outputs are still returned so the UI can show them):

| Failure | Stops before | Fields still populated |
|---|---|---|
| Lexical error | parser | `diagnostics` |
| Syntax error(s) | semantic analysis | `tokens`, `diagnostics` |
| Semantic error(s) | IR | `tokens`, `ast`, `symbols`, `diagnostics` |
| Success | — | everything up to the requested phase |

### 3.6 Data representation

- Tokens, AST nodes, symbols, and TAC instructions are **dataclasses** with a `to_dict()` (or generic converter) returning JSON-safe primitives.
- Line and column are 1-based everywhere.
- No phase mutates its input except the semantic analyzer, which only *adds annotations* (`type`, `symbol`) to AST nodes (RFC-0003 §3.4).

### 3.7 HTTP API contract (frontend-facing, summarized; full spec in RFC-0009)

```
POST /api/v1/compile
Request:
  { "source": "<MiniLang text>", "run": true, "optimize": true }

Response 200:
  {
    "ok": true,
    "tokens": [ { "type": "LET", "lexeme": "let", "line": 1, "column": 1 }, ... ],
    "ast": { "type": "Program", "body": [ ... ] },
    "symbols": [ { "name": "a", "kind": "variable", "type": "int", "scope": "global", "line": 1 } ],
    "tac": [ "t1 = 3 * 4", "result = t1" ],
    "optimized_tac": [ "result = 12" ],
    "python": "result = 12\n__nx_show(result)\n",
    "run": { "stdout": "12\n", "stderr": "", "exit_code": 0, "timed_out": false },
    "diagnostics": [
      { "phase": "Semantic Error", "code": "E3001", "severity": "error",
        "message": "use of undeclared variable 'x'", "line": 4, "column": 6 }
    ]
  }
```

Compile errors in the user's program are **HTTP 200 with `ok: false`** — they are normal results, not server failures. HTTP 4xx is for malformed requests (missing `source`, too large); 5xx for internal bugs.

### 3.8 Target abstraction (for future languages)

```python
class CodeGenerator(Protocol):
    target_name: str
    def generate(self, program: Program) -> str: ...
```

`pipeline.py` selects a generator by `options.target` from a dict defined in `pipeline.py` (not a global registry inside generators). Adding a target = one new module + tests + RFC.

### 3.9 Cross-cutting rules

1. **Determinism:** same input and options → same output (no timestamps, random ids, dict-order surprises).
2. **No global mutable state** (counters live on instances).
3. **Resource limits:** source ≤ 64 KB; AST depth ≤ 200 (parser raises E2006 "program is nested too deeply" instead of hitting Python's recursion limit); 50 diagnostics max per phase.
4. **Observability:** the pipeline records per-phase wall time in `CompileResult.timings` (added when the API lands) for the UI; compiler core never logs.
5. **Security:** user code runs only in the sandboxed runner (RFC-0009). The API process never executes it.

### 3.10 Repository layout

See `AGENTS.md` §5. The layout is part of this RFC's contract: module names and the import direction
`errors → tokens → lexer → ast_nodes → parser → symbols → semantic → ir → optimizer → codegen_python → runner → pipeline → api`.

## 4. Alternatives considered

1. **Parser generator (ANTLR/PLY/Lark).** Rejected: hides the concepts the project must demonstrate, adds a dependency, and complicates custom error messages.
2. **Single-pass compiler (parse and emit together).** Rejected: no AST, no semantic phase, no optimization — would not satisfy the project goals.
3. **Generate Python from TAC.** Rejected for readability reasons (§3.3).
4. **Use Python's `ast` module as the AST.** Rejected: couples the front end to the target and hurts future targets.
5. **Exceptions for all errors** (stop at first). Rejected for parser and semantic phases: users want multiple errors per run. Kept for the lexer (§RFC-0004 §5.1).
6. **Microservice per phase.** Rejected: unnecessary complexity for a library-sized compiler.

## 5. Drawbacks and risks

- Maintaining both an AST optimizer and a TAC optimizer is extra work; mitigated by sharing the folding rules and by scheduling TAC-level optimization as the last, optional stage.
- Strict phase boundaries mean some information (e.g. exact token positions for a node's end) must be threaded through the AST deliberately.
- The `CompileResult` JSON can be large for big programs; the 64 KB source cap bounds it.

## 6. Impact on other components

- RFC-0003 (AST), RFC-0004 (diagnostics), RFC-0005 (semantic) implement §3.4 contracts.
- RFC-0006/0007/0008/0009/0010 (planned) detail phases 4–7 and the frontend.

## 7. Test plan

- **Contract tests per phase:** assert each guarantee in §3.4 (e.g. exactly one `EOF`; every AST node has a position; every expression has a type after semantic analysis; generated Python passes `ast.parse`).
- **Pipeline tests:** stop rules (§3.5) for each failure kind.
- **Determinism test:** compile the same source twice; outputs are byte-identical.
- **Import-direction test:** a test scans `nexora/*.py` imports and fails on a backwards import.
- **End-to-end:** every `examples/*.mini` compiles, runs, and matches expected stdout.
