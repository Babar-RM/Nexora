# RFC-0001: MiniLang v1 Language Specification

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-21
- **Depends on:** —
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines **MiniLang v1**: its lexical structure, grammar, type system overview, runtime semantics, and mapping goals to Python. It is the single source of truth for what a valid MiniLang program is. The lexer, parser, semantic analyzer, and code generator MUST conform to it.

## 2. Motivation

Nexora translates MiniLang to Python through a real compiler pipeline. Without a precise language definition, each phase's author would invent rules, and the phases would disagree. A small, fully specified language also keeps the project finishable and testable.

Design goals:

1. **Small** — enough to demonstrate variables, expressions, control flow, functions, and output.
2. **Unambiguous** — one parse for every valid program; LL(1)-friendly grammar for recursive descent.
3. **Statically typed with inference** — so semantic analysis has real work to do.
4. **Mappable to Python** — every construct has a faithful, readable Python translation.
5. **Extensible** — leaves room for more targets (JavaScript, Java) later.

Non-goals for v1: classes, arrays/lists, `for` loops, `break`/`continue`, imports, user input, first-class functions, closures, nested functions, string formatting.

## 3. Detailed design

### 3.1 Lexical structure

**Source encoding:** UTF-8 text. Line endings `\n` or `\r\n` (the `\r` is treated as whitespace).

**Whitespace:** space, tab, `\r`, `\n`. Insignificant except as a token separator. Line numbers and columns are 1-based; a column counts characters.

**Comments:** `//` to end of line. There are no block comments in v1.

**Identifiers:** `[A-Za-z_][A-Za-z0-9_]*` (ASCII only). Case-sensitive.

**Keywords (reserved):**

```
let  if  else  while  function  return  show  true  false  and  or  not
```

**Predeclared type names (reserved):** `int`, `float`, `string`, `bool`, `void`. They are lexed as identifiers; the parser/semantic analyzer treat them as type names and reject them as variable/function/parameter names (E3015).

**Reserved prefix:** identifiers starting with `__nx_` are reserved for the compiler runtime (E3015).

**Literals:**

| Kind | Form | Examples |
|---|---|---|
| int | `[0-9]+` | `0`, `42` |
| float | `[0-9]+ "." [0-9]+` | `3.14`, `0.5` |
| string | `"` … `"` on a single line | `"hello"`, `"a\tb"` |
| bool | `true` \| `false` | |

- No leading `+`/`-` in literals: `-5` is unary minus applied to `5`.
- `.5`, `5.`, `1e3`, hex, and underscores in numbers are **not** valid.
- String escapes: `\n`, `\t`, `\"`, `\\`. Any other escape is a lexical error (E1003). A string cannot contain a raw newline (E1002).

**Operators and punctuation:**

```
+  -  *  /  %        arithmetic
== != <  <= >  >=    comparison
=                    assignment / initialization
:                    type annotation separator
(  )  {  }  ,  ;     punctuation
```

Words `and`, `or`, `not` are the logical operators (keywords). There are no `&&`, `||`, `!`.

#### 3.1.1 Required lexer amendment

The first lexer implementation (see build guide) predates this RFC. To conform, apply:

1. `tokens.py`: add `COLON = auto()` to the punctuation group of `TokenType`.
2. `lexer.py`: add `":": TokenType.COLON` to `SINGLE_CHAR_TOKENS`.
3. `lexer.py`: replace Unicode-aware checks (`str.isdigit`, `isalpha`, `isalnum`) with ASCII-only helpers. `"²".isdigit()` is `True` in Python but `int("²")` raises, which would crash the lexer.

```python
def _is_digit(ch: str) -> bool:
    return "0" <= ch <= "9"

def _is_alpha(ch: str) -> bool:
    return ("a" <= ch <= "z") or ("A" <= ch <= "Z") or ch == "_"

def _is_alnum(ch: str) -> bool:
    return _is_alpha(ch) or _is_digit(ch)
```

4. Add tests: `:` lexes to `COLON`; `let x: int = 1;` token sequence; a non-ASCII letter in an identifier position raises E1001.

### 3.2 Grammar (EBNF)

Notation: `{ x }` zero or more, `[ x ]` optional, `( a | b )` choice, quoted text = token.

```ebnf
program        = { topLevel } EOF ;

topLevel       = functionDecl | statement ;

statement      = letStmt
               | assignStmt
               | ifStmt
               | whileStmt
               | returnStmt
               | showStmt
               | exprStmt
               | block ;

block          = "{" { statement } "}" ;            (* no functionDecl inside blocks *)

letStmt        = "let" IDENT [ ":" typeName ] "=" expression ";" ;
assignStmt     = IDENT "=" expression ";" ;
ifStmt         = "if" "(" expression ")" block [ "else" ( ifStmt | block ) ] ;
whileStmt      = "while" "(" expression ")" block ;
returnStmt     = "return" [ expression ] ";" ;
showStmt       = "show" "(" expression ")" ";" ;
exprStmt       = expression ";" ;

functionDecl   = "function" IDENT "(" [ params ] ")" [ ":" typeName ] block ;
params         = param { "," param } ;
param          = IDENT ":" typeName ;
typeName       = IDENT ;                             (* validated semantically: int|float|string|bool *)

expression     = orExpr ;
orExpr         = andExpr { "or" andExpr } ;
andExpr        = notExpr { "and" notExpr } ;
notExpr        = "not" notExpr | equality ;
equality       = comparison { ( "==" | "!=" ) comparison } ;
comparison     = term { ( "<" | "<=" | ">" | ">=" ) term } ;
term           = factor { ( "+" | "-" ) factor } ;
factor         = unary { ( "*" | "/" | "%" ) unary } ;
unary          = "-" unary | call ;
call           = IDENT "(" [ arguments ] ")" | primary ;
arguments      = expression { "," expression } ;
primary        = INT | FLOAT | STRING | "true" | "false" | IDENT | "(" expression ")" ;
```

**Disambiguation rules**

- `assignStmt` vs `exprStmt`: if a statement starts with `IDENT` followed by `=`, it is an assignment. (One-token lookahead after the identifier.) Assignment is a **statement**, not an expression: `a = b = 3;` and `if (a = 3)` are syntax errors.
- `else if` is `else` followed by an `ifStmt`; the grammar has no dangling-else ambiguity because blocks are mandatory (braces required even for one statement).
- Equality and comparison operators are **non-associative in practice**: `a < b < c` parses (left-assoc) but fails type checking (`bool < int`, E3004).
- Calls apply only to identifiers (`f(1)(2)` is a syntax error). Functions are not values.
- A `functionDecl` inside a block is a syntax error (E2005): "functions can only be declared at top level".

**Operator precedence and associativity** (lowest → highest binding)

| Level | Operators | Assoc. |
|---|---|---|
| 1 | `or` | left |
| 2 | `and` | left |
| 3 | `not` | right (prefix) |
| 4 | `==` `!=` | left |
| 5 | `<` `<=` `>` `>=` | left |
| 6 | `+` `-` | left |
| 7 | `*` `/` `%` | left |
| 8 | unary `-` | right (prefix) |
| 9 | call, parentheses | — |

### 3.3 Types

MiniLang has four value types and one non-value type:

| Type | Values | Python mapping |
|---|---|---|
| `int` | arbitrary-precision integers | `int` |
| `float` | IEEE-754 double | `float` |
| `string` | immutable text | `str` |
| `bool` | `true`, `false` | `bool` |
| `void` | no value (only as a function return type) | `None` |

Rules (detailed typing table is in RFC-0005):

1. Every variable has exactly one type for its lifetime. The type is the annotation if present, otherwise the type of the initializer.
2. **No implicit conversions**, with one exception: **`int` widens to `float`** when initializing/assigning a `float` variable, passing an argument to a `float` parameter, returning from a `float` function, and in mixed arithmetic (`int + float` is `float`).
3. `if` and `while` conditions MUST be `bool`. There is no truthiness (`if (1)` is an error).
4. `string + string` concatenates. No other operator works on strings except comparison.
5. `and`, `or`, `not` take `bool` operands only and short-circuit (`and`/`or`).

### 3.4 Declarations, scope, and names

1. `let` MUST have an initializer. Uninitialized variables do not exist.
2. Scopes: the **global scope** (top level), a **function scope** (parameters + body), and a **block scope** for each `{ }`.
3. A variable is visible from its declaration to the end of its block.
4. **No shadowing.** A name may not be declared if the same name is visible from the current point (in any enclosing scope, including global variables and function names). This keeps Python generation correct, because Python has function scope, not block scope.
5. Two sibling blocks may both declare `x`.
6. Functions are declared at top level only and are **hoisted**: a function may be called from anywhere in the file, including before its declaration. Functions can be recursive. Two functions cannot share a name.
7. **Globals inside functions:** a function body may *read* a global variable only if the global is declared textually **before** the function. A function MUST NOT *assign* to a global variable (E3009). Pass values in as parameters and return results instead.
8. Parameters are local variables of the function's scope.

### 3.5 Statements — semantics

- **`let x [: T] = e;`** — evaluate `e`, declare `x` with type `T` (or the type of `e`), bind the value.
- **`x = e;`** — evaluate `e`, check assignable to `x`'s type, store.
- **`if (c) {A} else {B}`** — evaluate `c`; run `A` if true, otherwise `B` (if present).
- **`while (c) {B}`** — repeat `B` while `c` is true. There is no `break`/`continue` in v1.
- **`return e;`** / **`return;`** — leave the current function. `return` outside a function is an error (E3010). A non-void function MUST return a value on every path (E3012). A void function may use `return;` or fall off the end.
- **`show(e);`** — evaluate `e` (any value type, not `void`) and write its text form followed by a newline to standard output. Text forms: `int` → decimal; `float` → shortest round-trip decimal that always contains a `.` or exponent (e.g. `1.0`, `0.1`); `string` → raw text; `bool` → `true` or `false` (NOT `True`/`False`).
- **expression statement** — evaluate and discard. Typically a call to a function.
- **block** — new scope; statements run in order.

Top-level statements run top to bottom. There is no `main`. Function declarations produce no runtime effect when passed over.

### 3.6 Expression semantics

- Arithmetic `+ - * / %` on numbers: `int op int → int` for `+ - * %`; **`/` always yields `float`** (true division); any `float` operand makes the result `float`. `%` follows Python semantics (result has the sign of the divisor).
- Division or modulo by zero is a **runtime error** (R5001), not a compile error. The compiler MUST NOT fold it away (RFC-0007).
- Comparison `< <= > >=`: both numeric, or both `string` (lexicographic). Result `bool`.
- Equality `== !=`: both numeric (int/float compare by value), or same type among `string`/`bool`. Result `bool`.
- Unary `-` on `int`/`float`. `not` on `bool`.
- Calls evaluate arguments left to right, then call. Argument count and types must match the parameters (widening allowed `int → float`). Calling a `void` function is allowed only as an expression statement; using its result in an expression is E3013.
- Evaluation of operands is left to right.
- Integer overflow does not occur (arbitrary precision). Floats may produce `inf`/`nan` per IEEE-754 where Python does.
- Recursion depth is limited by the runtime; exceeding it is a runtime error (R5003).

### 3.7 Mapping to Python (informative; normative in RFC-0008)

| MiniLang | Python |
|---|---|
| `let x = 1;` | `x = 1` |
| `let p: float = 2;` | `p = float(2)` (widening made explicit) |
| `show(e);` | `__nx_show(e)` (prelude formats bools as `true`/`false`) |
| `if/else if/else` | `if` / `elif` / `else` |
| `while (c) { }` | `while c:` |
| `function f(a: int): int { }` | `def f(a):` |
| `and`/`or`/`not` | `and`/`or`/`not` |
| identifier named like a Python keyword/builtin used by output | renamed with trailing `_` |
| empty block | `pass` |

### 3.8 Complete example

```
// Compute and print factorials
function factorial(n: int): int {
    if (n <= 1) {
        return 1;
    }
    return n * factorial(n - 1);
}

let i = 1;
while (i <= 5) {
    show(factorial(i));
    i = i + 1;
}

let message = "done";
show(message + "!");
show(7 / 2);        // 3.5
show(7 % 2 == 1);   // true
```

Output:

```
1
2
6
24
120
done!
3.5
true
```

### 3.9 Invalid programs (non-exhaustive)

```
let x = 5            // E2002 missing ';'
let y = x + "a";     // E3004 cannot apply '+' to int and string
if (x) { }           // E3005 condition must be bool, found int
z = 3;               // E3001 undeclared variable 'z'
let x = 6;           // E3002 'x' is already declared
return 1;            // E3010 'return' outside of a function
function f(a: int): int { show(a); }   // E3012 not all paths return a value
```

## 4. Alternatives considered

1. **Dynamic typing** (like Python). Rejected: semantic analysis would have almost nothing to check, weakening the project.
2. **Mandatory type annotations everywhere** (`let x: int = 5;`). Rejected: noisy; inference for `let` is simple and valuable. Annotations are *required* only on function parameters, where inference would need whole-program analysis.
3. **Indentation-based blocks** (like Python). Rejected: makes lexing stateful (INDENT/DEDENT) and error recovery harder. Braces are simpler to teach and parse.
4. **Assignment as expression** (C-style). Rejected: causes `if (a = b)` bugs; statement form is safer.
5. **Allow block-scoped shadowing.** Rejected for v1: would require name mangling in generated Python to stay faithful. May be revisited in a later RFC.
6. **`&&`/`||`/`!`.** Rejected: word operators read clearly and match the project brief.

## 5. Drawbacks and risks

- Mandatory braces and semicolons are verbose but make parsing and recovery simple.
- No-shadowing is stricter than many languages; error message must explain it (see RFC-0004 hints).
- No arrays/for loops limits program variety. Acceptable for v1; the architecture supports adding them via RFC.
- `/` always producing `float` surprises C programmers; chosen to match Python and avoid silent truncation.

## 6. Impact on other components

- **Lexer:** amendment in §3.1.1.
- **Parser:** implements §3.2 exactly (RFC-0003 AST).
- **Semantic analyzer:** implements §3.3–3.6 (RFC-0005).
- **Code generator:** implements §3.7; defines prelude and name mangling (RFC-0008).
- **Optimizer:** must preserve §3.6 semantics, including runtime errors (RFC-0007).

## 7. Test plan

- Lexer: one test per token class, per escape, per lexical error; position tracking.
- Parser: one valid and one invalid fixture per grammar rule; precedence tests (`1 + 2 * 3`, `not a and b`, `-a * b`); `else if` chains; nested blocks; error recovery.
- Semantic: one test per rule in §3.3–3.6 and per code E3xxx.
- End-to-end: every program in `examples/` compiles, runs, and matches expected output, including the factorial example above.

## 8. Open questions

1. Should `for i in range(...)`-style loops be in v1.1? (Proposed: separate RFC after the core pipeline works.)
2. Should `void` be writable by users (`function f(): void`) or implicit only? (Proposed: implicit only in v1; `void` is reserved to keep the option open.)
3. Should `show` accept multiple arguments? (Proposed: no in v1.)
