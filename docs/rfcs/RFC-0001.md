# RFC-0001: MiniLang v1 Language Specification

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-21
- **Depends on:** —
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines **MiniLang v1**: its lexical structure, grammar, type system overview, runtime semantics, and mapping goals to Python. It is the single source of truth for what a valid MiniLang program is. The lexer, parser, semantic analyzer, and code generator MUST conform to it.

## 2. Motivation

Nexora translates MiniLang to Python through a real compiler pipeline. Without a precise language definition, each phase's author would invent rules, and the phases would disagree. A small, fully specified language also keeps the project finishable and testable.

Design goals:

1. **Small** — enough to demonstrate variables, expressions, control flow, functions, input, and output.
2. **Unambiguous** — one parse for every valid program; LL(1)-friendly grammar for recursive descent.
3. **Statically typed with inference** — so semantic analysis has real work to do.
4. **Mappable to Python** — every construct has a faithful, readable Python translation.
5. **Extensible** — leaves room for more targets (JavaScript, Java) later.
6. **Readable keywords** — English-word keywords (`make`, `when`, `during`, `task`, `give`, `show`, `ask`) reduce cognitive friction for new programmers.

Non-goals for v1: classes, arrays/lists, `for` loops, imports, first-class functions, closures, nested functions, string formatting.

## 3. Detailed design

### 3.1 Lexical structure

**Source encoding:** UTF-8 text. Line endings `\n` or `\r\n` (the `\r` is treated as whitespace).

**Whitespace:** space, tab, `\r`, `\n`. Insignificant except as a token separator. Line numbers and columns are 1-based; a column counts characters.

**Comments:** `//` to end of line. There are no block comments in v1.

**Identifiers:** `[A-Za-z_][A-Za-z0-9_]*` (ASCII only). Case-sensitive.

**Keywords (reserved):**

```
make  show  ask  when  otherwise  during  task  give  yes  no  both  either  not  empty  stop  skip
```

**Predeclared type names (reserved):** `int`, `float`, `string`, `bool`, `void`. They are lexed as identifiers; the parser/semantic analyzer treat them as type names and reject them as variable/task/parameter names (E3015).

**Reserved prefix:** identifiers starting with `__nx_` are reserved for the compiler runtime (E3015).

**Literals:**

| Kind | Form | Examples |
|---|---|---|
| int | `[0-9]+` | `0`, `42` |
| float | `[0-9]+ "." [0-9]+` | `3.14`, `0.5` |
| string | `"` … `"` on a single line | `"hello"`, `"a\tb"` |
| bool | `yes` \| `no` | |
| empty | `empty` | (the None value) |

- No leading `+`/`-` in literals: `-5` is unary minus applied to `5`.
- `.5`, `5.`, `1e3`, hex, and underscores in numbers are **not** valid.
- String escapes: `\n`, `\t`, `\"`, `\\`. Any other escape is a lexical error (E1003). A string cannot contain a raw newline (E1002).

**Operators and punctuation:**

```
+  -  *  /  %        arithmetic
== != <  <= >  >=    comparison
=                    assignment / initialization
:                    type annotation separator
(  )  {  }  ,  ;     punctuation
```

Words `both`, `either`, `not` are the logical operators (keywords). There are no `&&`, `||`, `!`.

#### 3.1.1 Required lexer amendment

The first lexer implementation (see build guide) predates this RFC. To conform, apply:

1. `tokens.py`: add `COLON = auto()` to the punctuation group of `TokenType`.
2. `lexer.py`: add `":"`: `TokenType.COLON` to `SINGLE_CHAR_TOKENS`.
3. `lexer.py`: replace Unicode-aware checks (`str.isdigit`, `isalpha`, `isalnum`) with ASCII-only helpers. `"²".isdigit()` is `True` in Python but `int("²")` raises, which would crash the lexer.

```python
def _is_digit(ch: str) -> bool:
    return "0" <= ch <= "9"

def _is_alpha(ch: str) -> bool:
    return ("a" <= ch <= "z") or ("A" <= ch <= "Z") or ch == "_"

def _is_alnum(ch: str) -> bool:
    return _is_alpha(ch) or _is_digit(ch)
```

4. Update the `KEYWORDS` map in `tokens.py` to the new keyword set:

```python
KEYWORDS: dict[str, TokenType] = {
    "make":      TokenType.MAKE,
    "show":      TokenType.SHOW,
    "ask":       TokenType.ASK,
    "when":      TokenType.WHEN,
    "otherwise": TokenType.OTHERWISE,
    "during":    TokenType.DURING,
    "task":      TokenType.TASK,
    "give":      TokenType.GIVE,
    "yes":       TokenType.YES,
    "no":        TokenType.NO,
    "both":      TokenType.BOTH,
    "either":    TokenType.EITHER,
    "not":       TokenType.NOT,
    "empty":     TokenType.EMPTY,
    "stop":      TokenType.STOP,
    "skip":      TokenType.SKIP,
}
```

5. Add tests: `:` lexes to `COLON`; `make x: int = 1;` token sequence; a non-ASCII letter in an identifier position raises E1001.

### 3.2 Grammar (EBNF)

Notation: `{ x }` zero or more, `[ x ]` optional, `( a | b )` choice, quoted text = token.

```ebnf
program        = { topLevel } EOF ;

topLevel       = taskDecl | statement ;

statement      = makeStmt
               | assignStmt
               | whenStmt
               | duringStmt
               | giveStmt
               | showStmt
               | askStmt
               | stopStmt
               | skipStmt
               | exprStmt
               | block ;

block          = "{" { statement } "}" ;            (* no taskDecl inside blocks *)

makeStmt       = "make" IDENT [ ":" typeName ] "=" expression ";" ;
assignStmt     = IDENT "=" expression ";" ;
whenStmt       = "when" "(" expression ")" block [ "otherwise" ( whenStmt | block ) ] ;
duringStmt     = "during" "(" expression ")" block ;
giveStmt       = "give" [ expression ] ";" ;
showStmt       = "show" "(" expression ")" ";" ;
askStmt        = "ask" IDENT ":" typeName ";" ;
stopStmt       = "stop" ";" ;
skipStmt       = "skip" ";" ;
exprStmt       = expression ";" ;

taskDecl       = "task" IDENT "(" [ params ] ")" [ ":" typeName ] block ;
params         = param { "," param } ;
param          = IDENT ":" typeName ;
typeName       = IDENT ;                             (* validated semantically: int|float|string|bool *)

expression     = eitherExpr ;
eitherExpr     = bothExpr { "either" bothExpr } ;
bothExpr       = notExpr { "both" notExpr } ;
notExpr        = "not" notExpr | equality ;
equality       = comparison { ( "==" | "!=" ) comparison } ;
comparison     = term { ( "<" | "<=" | ">" | ">=" ) term } ;
term           = factor { ( "+" | "-" ) factor } ;
factor         = unary { ( "*" | "/" | "%" ) unary } ;
unary          = "-" unary | call ;
call           = IDENT "(" [ arguments ] ")" | primary ;
arguments      = expression { "," expression } ;
primary        = INT | FLOAT | STRING | "yes" | "no" | "empty" | IDENT | "(" expression ")" ;
```

**Disambiguation rules**

- `assignStmt` vs `exprStmt`: if a statement starts with `IDENT` followed by `=`, it is an assignment. (One-token lookahead after the identifier.) Assignment is a **statement**, not an expression: `a = b = 3;` and `when (a = 3)` are syntax errors.
- `otherwise when` is `otherwise` followed by a `whenStmt`; the grammar has no dangling-else ambiguity because blocks are mandatory (braces required even for one statement).
- Equality and comparison operators are **non-associative in practice**: `a < b < c` parses (left-assoc) but fails type checking (`bool < int`, E3004).
- Calls apply only to identifiers (`f(1)(2)` is a syntax error). Tasks are not values.
- A `taskDecl` inside a block is a syntax error (E2005): "tasks can only be declared at top level".
- `stop` and `skip` are only valid inside a `during` body (E3017, E3018 respectively).

**Operator precedence and associativity** (lowest → highest binding)

| Level | Operators | Assoc. |
|---|---|---|
| 1 | `either` | left |
| 2 | `both` | left |
| 3 | `not` | right (prefix) |
| 4 | `==` `!=` | left |
| 5 | `<` `<=` `>` `>=` | left |
| 6 | `+` `-` | left |
| 7 | `*` `/` `%` | left |
| 8 | unary `-` | right (prefix) |
| 9 | call, parentheses | — |

### 3.3 Types

MiniLang has four value types, an empty type, and one non-value type:

| Type | Values | Python mapping |
|---|---|---|
| `int` | arbitrary-precision integers | `int` |
| `float` | IEEE-754 double | `float` |
| `string` | immutable text | `str` |
| `bool` | `yes`, `no` | `bool` |
| `empty` | the absence of a value | `None` |
| `void` | no value (only as a task return type) | *(no value)* |

Rules (detailed typing table is in RFC-0005):

1. Every variable has exactly one type for its lifetime. The type is the annotation if present, otherwise the type of the initializer.
2. **No implicit conversions**, with one exception: **`int` widens to `float`** when initializing/assigning a `float` variable, passing an argument to a `float` parameter, returning from a `float` task, and in mixed arithmetic (`int + float` is `float`).
3. `when` and `during` conditions MUST be `bool`. There is no truthiness (`when (1)` is an error).
4. `string + string` concatenates. No other operator works on strings except comparison.
5. `both`, `either`, `not` take `bool` operands only and short-circuit (`both`/`either`).
6. `ask x: T` reads a line from stdin and stores the result as type `T`; only `int`, `float`, and `string` are accepted as `T` for `ask` (E3019).

### 3.4 Declarations, scope, and names

1. `make` MUST have an initializer. Uninitialized variables do not exist.
2. `ask` declares a variable at the point of the statement; the type annotation is required.
3. Scopes: the **global scope** (top level), a **task scope** (parameters + body), and a **block scope** for each `{ }`.
4. A variable is visible from its declaration to the end of its block.
5. **No shadowing.** A name may not be declared if the same name is visible from the current point (in any enclosing scope, including global variables and task names). This keeps Python generation correct, because Python has function scope, not block scope.
6. Two sibling blocks may both declare `x`.
7. Tasks are declared at top level only and are **hoisted**: a task may be called from anywhere in the file, including before its declaration. Tasks can be recursive. Two tasks cannot share a name.
8. **Globals inside tasks:** a task body may *read* a global variable only if the global is declared textually **before** the task. A task MUST NOT *assign* to a global variable (E3009). Pass values in as parameters and return results instead.
9. Parameters are local variables of the task's scope.

### 3.5 Statements — semantics

- **`make x [: T] = e;`** — evaluate `e`, declare `x` with type `T` (or the type of `e`), bind the value.
- **`x = e;`** — evaluate `e`, check assignable to `x`'s type, store.
- **`ask x: T;`** — read one line from stdin, parse it as `T`, declare and bind `x`. At runtime, invalid input raises R5006.
- **`when (c) {A} otherwise {B}`** — evaluate `c`; run `A` if `yes`, otherwise `B` (if present).
- **`during (c) {B}`** — repeat `B` while `c` is `yes`.
- **`stop;`** — exit the immediately enclosing `during` loop. Error outside a loop (E3017).
- **`skip;`** — skip the rest of the current `during` iteration and re-evaluate the condition. Error outside a loop (E3018).
- **`give e;`** / **`give;`** — leave the current task. `give` outside a task is an error (E3010). A non-void task MUST give a value on every path (E3012). A void task may use `give;` or fall off the end.
- **`show(e);`** — evaluate `e` (any value type, not `void`) and write its text form followed by a newline to standard output. Text forms: `int` → decimal; `float` → shortest round-trip decimal that always contains a `.` or exponent (e.g. `1.0`, `0.1`); `string` → raw text; `bool` → `yes` or `no` (NOT `True`/`False`); `empty` → `empty`.
- **expression statement** — evaluate and discard. Typically a call to a task.
- **block** — new scope; statements run in order.

Top-level statements run top to bottom. There is no `main`. Task declarations produce no runtime effect when passed over.

### 3.6 Expression semantics

- Arithmetic `+ - * / %` on numbers: `int op int → int` for `+ - * %`; **`/` always yields `float`** (true division); any `float` operand makes the result `float`. `%` follows Python semantics (result has the sign of the divisor).
- Division or modulo by zero is a **runtime error** (R5001), not a compile error. The compiler MUST NOT fold it away (RFC-0007).
- Comparison `< <= > >=`: both numeric, or both `string` (lexicographic). Result `bool`.
- Equality `== !=`: both numeric (int/float compare by value), or same type among `string`/`bool`/`empty`. Result `bool`.
- Unary `-` on `int`/`float`. `not` on `bool`.
- Calls evaluate arguments left to right, then call. Argument count and types must match the parameters (widening allowed `int → float`). Calling a `void` task is allowed only as an expression statement; using its result in an expression is E3013.
- Evaluation of operands is left to right.
- Integer overflow does not occur (arbitrary precision). Floats may produce `inf`/`nan` per IEEE-754 where Python does.
- Recursion depth is limited by the runtime; exceeding it is a runtime error (R5003).
- `empty` literal has type `empty`. `empty == empty` is `yes`.

### 3.7 Mapping to Python (informative; normative in RFC-0008)

| MiniLang | Python |
|---|---|
| `make x = 1;` | `x = 1` |
| `make p: float = 2;` | `p = float(2)` (widening made explicit) |
| `ask name: string;` | `name = input()` |
| `ask age: int;` | `age = int(input())` |
| `ask price: float;` | `price = float(input())` |
| `show(e);` | `__nx_show(e)` (prelude formats bools as `yes`/`no`, `empty` as `empty`) |
| `when/otherwise when/otherwise` | `if` / `elif` / `else` |
| `during (c) { }` | `while c:` |
| `task f(a: int): int { }` | `def f(a):` |
| `both`/`either`/`not` | `and`/`or`/`not` |
| `yes` / `no` | `True` / `False` |
| `empty` | `None` |
| `stop;` | `break` |
| `skip;` | `continue` |
| `give e;` | `return e` |
| identifier named like a Python keyword/builtin used by output | renamed with trailing `_` |
| empty block | `pass` |

### 3.8 Complete example

```
// Compute and print factorials
task factorial(n: int): int {
    when (n <= 1) {
        give 1;
    }
    give n * factorial(n - 1);
}

make i = 1;
during (i <= 5) {
    show(factorial(i));
    i = i + 1;
}

make message = "done";
show(message + "!");
show(7 / 2);         // 3.5
show(7 % 2 == 1);    // yes

ask name: string;
show("Hello " + name);
```

### 3.9 Example with stop and skip

```
make i = 1;
during (i <= 10) {
    when (i == 5) {
        stop;
    }
    when (i == 3) {
        i = i + 1;
        skip;
    }
    show(i);
    i = i + 1;
}
// prints: 1 2 4  (skips 3, stops before 5)
```

### 3.10 Invalid programs (non-exhaustive)

```
make x = 5            // E2002 missing ';'
make y = x + "a";     // E3004 cannot apply '+' to int and string
when (x) { }          // E3005 condition must be bool, found int
z = 3;                // E3001 undeclared variable 'z'
make x = 6;           // E3002 'x' is already declared
give 1;               // E3010 'give' outside of a task
task f(a: int): int { show(a); }   // E3012 not all paths return a value
stop;                 // E3017 'stop' used outside of a 'during' loop
skip;                 // E3018 'skip' used outside of a 'during' loop
ask x: bool;          // E3019 'ask' does not support type 'bool'
```

## 4. Alternatives considered

1. **Dynamic typing** (like Python). Rejected: semantic analysis would have almost nothing to check, weakening the project.
2. **Mandatory type annotations everywhere** (`make x: int = 5;`). Rejected: noisy; inference for `make` is simple and valuable. Annotations are *required* only on task parameters and `ask` statements, where inference would need whole-program or runtime analysis.
3. **Indentation-based blocks** (like Python). Rejected: makes lexing stateful (INDENT/DEDENT) and error recovery harder. Braces are simpler to teach and parse.
4. **Assignment as expression** (C-style). Rejected: causes `when (a = b)` bugs; statement form is safer.
5. **Allow block-scoped shadowing.** Rejected for v1: would require name mangling in generated Python to stay faithful. May be revisited in a later RFC.
6. **`&&`/`||`/`!`.** Rejected: word operators read clearly and match the project brief.
7. **`if`/`else`/`while` instead of `when`/`otherwise`/`during`.** Rejected: the custom English vocabulary is a deliberate design choice that differentiates MiniLang and reduces confusion with Python syntax.

## 5. Drawbacks and risks

- Mandatory braces and semicolons are verbose but make parsing and recovery simple.
- No-shadowing is stricter than many languages; error message must explain it (see RFC-0004 hints).
- `ask` supports only `int`, `float`, `string`; programmers wanting `bool` input must read a string and convert it.
- `stop`/`skip` (break/continue) are v1 features; `always_returns` analysis already conservatively treats `during` as never returning, so adding `stop` does not complicate return-path analysis.

## 6. Impact on other components

- **Lexer:** keyword set replaced (§3.1.1). New tokens: `MAKE SHOW ASK WHEN OTHERWISE DURING TASK GIVE YES NO BOTH EITHER NOT EMPTY STOP SKIP`.
- **Parser:** implements §3.2 exactly (RFC-0003 AST). New grammar rules: `askStmt`, `stopStmt`, `skipStmt`.
- **Semantic analyzer:** implements §3.3–3.6 (RFC-0005). New errors E3017, E3018, E3019.
- **Code generator:** implements §3.7; defines prelude and name mangling (RFC-0008). New mappings for `ask`, `stop`, `skip`, `yes`, `no`, `empty`.
- **Optimizer:** must preserve §3.6 semantics, including runtime errors (RFC-0007).

## 7. Test plan

- Lexer: one test per token class, per escape, per lexical error; position tracking. Verify all 16 keywords lex correctly.
- Parser: one valid and one invalid fixture per grammar rule; precedence tests (`1 + 2 * 3`, `not a both b`, `-a * b`); `otherwise when` chains; nested blocks; `stop`/`skip` inside and outside `during`; error recovery.
- Semantic: one test per rule in §3.3–3.6 and per code E3001–E3019.
- End-to-end: every program in `examples/` compiles, runs, and matches expected output, including the factorial example above.

## 8. Open questions

1. Should `during/stop/skip` support labelled loops (break to outer loop)? (Proposed: no in v1.)
2. Should `ask` support multiple comma-separated variables? (Proposed: no in v1 — one binding per `ask`.)
3. Should `show` accept multiple arguments? (Proposed: no in v1.)
4. Should `void` be writable by users (`task f(): void`) or implicit only? (Proposed: implicit only in v1; `void` is reserved.)
5. Should `empty` be its own type or part of every nullable type? (Proposed: its own singleton type in v1; nullability generics are future work.)
