# RFC-0010: Frontend (Editor and Compiler Visualizer)

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-28
- **Depends on:** RFC-0002, RFC-0004, RFC-0006, RFC-0007, RFC-0008, RFC-0009
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines the Nexora web application: a code editor for MiniLang, a compile/run workflow, and a **compiler visualizer** that shows what every phase produced (tokens, AST, symbols, TAC, CFG, optimization notes, generated Python, program output, diagnostics) with cross-highlighting between the source and each view. It specifies the tech stack, screen layout, state model, API integration, interaction details, accessibility, performance and security requirements, testing, and the build order. The frontend is built **last**, after the backend API (RFC-0009) works.

## 2. Motivation

The project's educational value is that users can *see* how source code becomes Python. A compiler that only prints a result hides everything interesting. The frontend turns the pipeline's already-serializable phase outputs (RFC-0002 §3.6) into an explorable interface, and it is the face of the project in the demo and portfolio.

Goals:

1. Write MiniLang comfortably (highlighting, line numbers, error squiggles).
2. Compile, see errors where they belong, and run with one action.
3. Understand each compiler phase by inspecting its output and linking it back to the source.
4. Work on a laptop and a phone, keyboard-only, in light and dark themes.

Non-goals (v1): user accounts, saving programs on the server, collaboration, multi-file projects, a debugger, mobile-native apps.

## 3. Detailed design

### 3.1 Tech stack

| Concern | Choice | Reason |
|---|---|---|
| Build tool | **Vite** | fast dev server, simple config |
| UI framework | **React 18 + TypeScript (strict)** | component model; types catch API drift |
| Editor | **Monaco Editor** via `@monaco-editor/react` | line numbers, markers, hover, themes, custom language |
| Styling | **Tailwind CSS** with CSS variables for theme tokens | quick, consistent; theming without rebuilds |
| State | **Zustand** | tiny store, no boilerplate |
| Data fetching | native `fetch` + `AbortController` | one POST endpoint does not need a query library |
| API types | **`openapi-typescript`** generated from `/openapi.json` | single source of truth with the backend |
| Panels | `react-resizable-panels` | resizable split layout |
| Virtualization | `react-window` | long token/TAC tables |
| Graph views (CFG, AST graph) | **`@xyflow/react`** (React Flow) + `dagre` for layout | loaded lazily, only when the tab is opened |
| Unit/component tests | **Vitest + React Testing Library** | |
| End-to-end tests | **Playwright** | |
| Lint/format | ESLint + Prettier | |

Monaco, React Flow, and `dagre` are **code-split** (dynamic import) so the initial bundle stays small (§3.10).

The frontend contains **no compiler logic** (rules.md §16): it never tokenizes, parses, or type-checks MiniLang, with one exception — syntax *highlighting* uses a Monarch tokenizer, which is cosmetic and built from `GET /api/v1/language`, so it follows the real keyword list.

- **Desktop (≥ 1024 px):** editor left, tabbed inspector right, problems panel below; both splits are resizable and sizes persist in `localStorage`.
- **Tablet/phone (< 1024 px):** single column; the toolbar has a segmented control `Editor | Inspector | Problems`.
- The *Output* tab is selected automatically after **Run**; the *Problems* panel is expanded automatically when diagnostics contain errors.

### 3.4 State model

```ts
type Phase = "idle" | "compiling" | "running";

interface NexoraState {
  source: string;                       // editor content
  options: { optimize: boolean };
  phase: Phase;
  result: CompileResult | null;         // last response (API type)
  stale: boolean;                       // true if source changed after `result`
  apiError: { code: string; message: string } | null;   // 4xx/5xx/network
  selection: SourceRange | null;        // cross-highlight target (line/column/length)
  activeTab: TabId;
  theme: "light" | "dark" | "system";
  examples: Example[];
  language: LanguageInfo | null;
  // actions: setSource, compile(run: boolean), selectRange, setTab, ...
}
```

- `compile(run)` aborts any in-flight request (`AbortController`), sets `phase`, calls the API, and stores the result. A response that arrives for an aborted request is ignored.
- `stale` becomes `true` on any edit; panels show a subtle “out of date” badge instead of hiding data (so users can compare while editing).
- Derived data (e.g. AST tree expansion state) lives in component state, not in the global store.

### 3.5 Workflow

| Action | Trigger | Request |
|---|---|---|
| **Compile** | button, `Ctrl/⌘+Enter` | `POST /compile {run:false, optimize}` |
| **Run** | button, `Ctrl/⌘+Shift+Enter` | `POST /compile {run:true, optimize}` |
| **Live check** (optional toggle, default on) | 600 ms after the last keystroke | `POST /compile {run:false, emit:["tokens","diagnostics"…]}` — a light request that updates squiggles without producing the heavy phases |
| **Load example** | examples menu | replaces the source (confirm if the editor has unsaved edits) |
| **Share** | toolbar button | copies a URL with the source in the hash (`#src=<base64url(deflate(source))>`), max 8 KB of encoded source; larger programs show “too large to share via link” |
| **Reset** | menu | restores the last loaded example or an empty program |

- The editor content persists in `localStorage` (`nexora:source`) with try/catch around every access.
- The initial source is, in order: URL hash → `localStorage` → the “Hello” example.
- While `phase !== "idle"` the Compile/Run buttons show a spinner and are disabled (Run additionally shows “running… up to 5 s”).

### 3.6 API integration

- Types come from `schema.d.ts`, generated by `npm run gen:api` (`openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts`). CI fails if the generated file is out of date.
- Base URL from `VITE_API_BASE_URL` (default `http://localhost:8000`).
- Error mapping (RFC-0009 §3.3):

| Condition | UI behaviour |
|---|---|
| `200`, `ok:false` | show diagnostics (normal result; not an error banner) |
| `200`, `ok:true`, `run.diagnostics[0]` | show runtime error in Output + Problems, with line marker |
| `413` | banner “program is larger than 64 KB” |
| `429` | banner “too many requests — try again in N s” using `Retry-After` |
| `503 busy` | banner “server is busy running other programs, try again” |
| `500` | banner “something went wrong on the server” + request id from `X-Request-ID` |
| network failure/timeout (10 s) | banner “cannot reach the Nexora server” with a Retry button |

### 3.7 Editor features

**Language support.** `monarch.ts` registers language id `minilang` using `keywords`, `types`, `operators` from `/language`: comments `//`, strings with escapes (`\n \t \" \\`), numbers (int and float), keywords, operators, type names, task names after `task`. Auto-closing for `()`, `{}`, `""`; bracket matching; indentation of 4 spaces; `//` toggles comment with `Ctrl/⌘+/`.

**Diagnostics as markers.** Every diagnostic becomes a Monaco marker: `startLineNumber = line`, `startColumn = column`, `endColumn = column + length`; severity `Error`/`Warning`; message `[E3001] …`; the `hint` is appended on a new line. Markers are cleared on every new result and reapplied. Hovering shows the message; the Problems panel lists the same entries, and clicking an entry moves the cursor there (`selectRange`).

**Cross-highlighting (the signature feature).**
- Hover/select a **token row**, **AST node**, **symbol**, **TAC instruction** (uses `line`), or **Python line** (uses `python_line_map`) → highlight the corresponding range/line in the editor with a decoration.
- Place the cursor in the editor → highlight the matching AST node (innermost node whose range contains the cursor; nodes have `line`/`column`, and the innermost-start heuristic uses node start positions) and the TAC/Python lines mapped to that source line.
- Highlights are decorations only; they never modify the source.

**Quick actions.** Format-on-demand is out of scope (no formatter in v1). “Go to definition” for identifiers uses `symbols[].line`.

### 3.8 Panels

| Panel | Content | Details |
|---|---|---|
| **Output** | `run.stdout` in a monospace block; exit status chip; duration; runtime diagnostic; “Run to see output” empty state | text only; large outputs virtualized; “output truncated” notice |
| **Python** | generated code in a read-only Monaco instance (language `python`) | gutter shows the originating MiniLang line from `python_line_map`; **Copy** and **Download .py** buttons (download via `Blob`, client-side) |
| **Tokens** | table: #, type, lexeme, line:col | virtualized; filter box; click → highlight |
| **AST** | collapsible tree (default) with node type, key fields, and `resolved_type` badge; optional **Graph** toggle (React Flow, lazy) | expand/collapse all; search; click → highlight; nodes with semantic type annotations show the type |
| **Symbols** | table: name, kind, type (`(int, int) -> int` for functions), scope, declared at | sortable; click → go to declaration |
| **TAC** | listing grouped by basic block (B0, B1, …) with line numbers; toggle **Optimized**; **Diff** view shows before/after side by side with changed lines marked | uses `tac`, `optimized_tac`, `cfg` |
| **CFG** | directed graph of basic blocks per function (React Flow + dagre); edges labeled `true`/`false` for conditional jumps | function selector; lazy-loaded |
| **Optimization** | list of `OptimizationNote`s: level badge (AST/TAC), line, `before → after`; filter by level; banner “TAC optimization is shown for study; the generated Python comes from the optimized AST” (RFC-0007 §5) | click → highlight source line |
| **Problems** | diagnostics grouped by severity; counts in the tab title (`Problems (2)`) with an `aria-live="polite"` announcement of count changes | filter errors/warnings; code chips link to `docs` text from `/language` |

Empty and error states: every panel has a clear empty state (“Compile to see tokens”) and, when the pipeline stopped early (RFC-0002 §3.5), a notice such as “Parsing failed — no AST available” instead of a blank area.

### 3.9 Security

1. **No HTML injection:** program output, diagnostics, source, and generated code are rendered as text (React escapes by default). `dangerouslySetInnerHTML` is forbidden (ESLint rule `react/no-danger: error`).
2. The share-link decoder validates length and structure before decoding and never evaluates anything; failures fall back to the default example.
3. Content-Security-Policy (set by the host/server): `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self' <api-origin>; img-src 'self' data:; worker-src 'self' blob:` (Monaco workers need `blob:`).
4. No secrets or API keys in the bundle; `VITE_*` variables are public by definition.
5. `localStorage` access is wrapped in try/catch and treated as untrusted input (schema-checked on read).
6. Downloads are generated client-side from already-received text.

### 3.10 Performance budgets

| Metric | Target |
|---|---|
| Initial JS (excluding Monaco and graph libs), gzip | ≤ 300 KB |
| Time to interactive editor on a mid-range laptop | ≤ 2.5 s on a cached load |
| Compile round trip for a 200-line program (local backend) | ≤ 300 ms |
| Typing latency | no frame > 50 ms while live-check is active |
| Large result rendering (2,000 tokens, 5,000 AST nodes) | virtualized or lazily expanded; no jank on tab switch |

Techniques: lazy-loaded Monaco and graph libraries; memoized panels (`React.memo` + stable selectors); debounce 600 ms; abort stale requests; virtualization for long lists; AST tree renders collapsed beyond depth 3.

### 3.11 Accessibility and responsiveness

- WCAG 2.1 **AA** contrast in both themes; theme tokens defined as CSS variables; Monaco themes derived from them. “System” theme follows `prefers-color-scheme`.
- Tabs follow the ARIA tabs pattern (`role="tablist"`, arrow-key navigation, `aria-selected`, `aria-controls`).
- Everything operable by keyboard; visible focus rings; a skip link to the editor; shortcuts listed in a help dialog (`?`).
- Severity is never conveyed by color alone (icon + text: “Error”, “Warning”).
- Respect `prefers-reduced-motion` (no animated transitions of graphs).
- Monaco's built-in screen-reader mode is enabled when the user turns it on (`Alt+F1`); the Problems panel provides the same information as text.
- Touch targets ≥ 44 × 44 px on small screens.

### 3.12 Build order (frontend milestones)

1. **M1 — Skeleton:** Vite + React + TS + Tailwind; layout; theme toggle; health check against the API.
2. **M2 — Editor + Compile:** Monaco with MiniLang highlighting; `compile()`; diagnostics as markers; Problems panel.
3. **M3 — Run and Python:** Run button; Output and Python panels; examples menu.
4. **M4 — Inspectors:** Tokens, AST tree, Symbols panels; cross-highlighting.
5. **M5 — IR and optimization:** TAC (+ diff), CFG, Optimization panels.
6. **M6 — Polish:** share links, keyboard shortcuts, accessibility pass, responsive layout, error banners, E2E tests, deployment.

Stretch (after M6, separate RFC if pursued): *pipeline stepper* animation that walks one expression through each phase; a “learn mode” with explanations of each tab; Pyodide-based in-browser run as an alternative to server execution.

### 3.13 Build and deployment

- `npm run dev` (Vite, port 5173) against `uvicorn api:app --reload` (port 8000).
- `npm run build` outputs `dist/`; in production either serve `dist/` from the same origin as the API (FastAPI `StaticFiles`, avoids CORS) or host it separately and set `NEXORA_CORS_ORIGINS`.
- Environment: `VITE_API_BASE_URL`.
- CI runs: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, the API-types freshness check, and Playwright against a started backend.

## 4. Alternatives considered

1. **Plain HTML + JavaScript + CodeMirror.** Simpler to start, but the amount of interactive state (cross-highlighting, many panels, async requests) benefits from React and TypeScript. CodeMirror 6 remains an acceptable replacement for Monaco if bundle size becomes a problem.
2. **Next.js.** SSR adds nothing for a client-only tool; Vite is leaner.
3. **Redux Toolkit.** More ceremony than needed; Zustand is sufficient.
4. **React Query/TanStack Query.** Valuable for many endpoints; here one POST plus two cached GETs do not justify it.
5. **Implementing the lexer in JavaScript for live highlighting/errors.** Rejected: duplicates compiler logic and can drift (rules.md §16). Highlighting is cosmetic and driven by `/language`; real errors always come from the backend.
6. **A native desktop app (Tauri/Electron).** Out of scope for v1.
7. **Rendering the AST only as JSON.** Rejected: the project's point is to make structure visible; a tree and a graph are far clearer.

## 5. Drawbacks and risks

- Monaco is heavy (~MBs); mitigated by lazy loading and caching, with CodeMirror as a fallback.
- Cross-highlighting depends on every token, AST node, and TAC instruction carrying accurate `line`/`column` (RFC-0003 §3.3, RFC-0006 §3.7). Bugs in positions show up visually, which is useful but demands careful tests.
- Live-check doubles server load per user; it is debounced, uses `emit` subsetting, shares the compile rate limit (60/min), and can be switched off in the UI.
- Generated API types require running the generator when the backend schema changes; CI enforces it.

## 6. Impact on other components

- **Backend:** must expose accurate positions (including `length` in diagnostics), `/language`, `/examples`, `emit` subsetting, CORS, and the error shapes of RFC-0009. The AST JSON must include `resolved_type` (RFC-0003 §3.6).
- **rules.md §16:** this RFC operationalizes those rules.
- **AGENTS.md:** the frontend gets its own short section when work starts.

## 7. Test plan

**Unit / component (Vitest + RTL)**
- Store: compile success, compile failure, aborted request ignored, `stale` handling, API error mapping.
- `markers.ts`: diagnostics → Monaco markers (line/column/length/severity, hint appended).
- `monarch.ts`: tokenization of keywords, strings with escapes, numbers, comments, and a keyword added to `/language` becomes highlighted.
- Panels: each renders data, empty state, and “phase did not run” state; AST expand/collapse; token filter; symbol sorting; TAC diff marks changed lines.
- Share links: round trip, oversize rejection, corrupt hash fallback.
- Accessibility: `jest-axe` on each panel (no violations); tab keyboard navigation test.

**End-to-end (Playwright, against a real backend)**
1. Load the “Hello” example, Compile, see tokens/AST/Python; Run, see output.
2. Introduce `make x = ;` → squiggle on the right line, Problems shows E2001, clicking jumps to the line.
3. Undeclared variable → E3001 marker; fix it → markers disappear.
4. `during (yes) {}` → Run shows the time-limit error after ~5 s; UI recovers and Run works again.
5. Rate limit (backend configured low) → banner with retry time.
6. Cross-highlight: clicking an AST node highlights its source; clicking a Python line highlights the MiniLang line.
7. Theme toggle and keyboard shortcuts; mobile viewport layout switch.
8. Share link: open a copied URL in a new context → same source loads.

**Visual regression** (optional): Playwright screenshots of the main layout in light and dark themes.
