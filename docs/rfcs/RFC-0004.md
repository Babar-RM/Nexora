# RFC-0004: Diagnostics, Error Codes, and Recovery

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-21
- **Depends on:** RFC-0001, RFC-0002
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines how Nexora reports problems: the `Diagnostic` data structure, severity levels, the full list of stable error codes, message style, the plain-text rendering with source excerpts, the JSON shape for the API, and the recovery strategy of each phase (lexer fail-fast, parser panic-mode, semantic error collection).

## 2. Motivation

Users write invalid programs most of the time they use a compiler. Good diagnostics are what make Nexora feel like a real tool. They are also how three different phases surface problems to the same UI, so they must share one format. Stable codes let tests, docs, and the frontend refer to errors unambiguously.

## 3. Detailed design

### 3.1 The `Diagnostic` structure

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Diagnostic:
    phase: str                 # "Lexical Error" | "Syntax Error" | "Semantic Error" | "Warning" | "Runtime Error"
    code: str                  # "E1001", "E2002", "E3004", "W4001", "R5001"
    severity: str              # "error" | "warning"
    message: str
    line: int | None = None    # 1-based
    column: int | None = None  # 1-based
    length: int = 1            # characters to underline
    hint: str | None = None    # optional suggestion

    def to_dict(self) -> dict: ...
```

Exceptions remain for control flow and are thin wrappers around a `Diagnostic`:

```python
class NexoraError(Exception):
    def __init__(self, diagnostic: Diagnostic): ...
    # LexerError, ParserError, SemanticError subclass NexoraError

class InternalCompilerError(Exception):
    """A bug in Nexora itself. Never shown as a user mistake."""
```

A `DiagnosticBag` collects diagnostics for a phase:

```python
class DiagnosticBag:
    MAX_ERRORS = 50
    def error(self, code, message, line, column, length=1, hint=None, phase=...): ...
    def warning(self, code, message, line, column, length=1, hint=None): ...
    @property
    def has_errors(self) -> bool: ...
    def items(self) -> list[Diagnostic]: ...   # sorted by (line, column)
```

When `MAX_ERRORS` is reached the bag appends one final diagnostic, `too many errors (50); stopping`, and ignores further reports.

### 3.2 Position conventions

- Line and column are **1-based**; a column counts characters from the start of the line.
- The position is the **start** of the offending token or node (RFC-0003 §3.3).
- “Unexpected end of input” is reported at the EOF token position.
- For a missing token (e.g. `;`), the position is the **end of the previous token** (where the token should have been), not the start of the next token. This makes “missing semicolon” point at the line that needs fixing.

### 3.3 Severity

| Severity | Meaning | Effect |
|---|---|---|
| `error` | Program is invalid or failed | Compilation stops before the next phase |
| `warning` | Valid but suspicious | Compilation continues; shown in UI |

### 3.4 Error codes (stable; never reused or renumbered)

**Lexical — `E1xxx` (phase “Lexical Error”)**

| Code | Meaning | Example message |
|---|---|---|
| E1001 | Unexpected character | `unexpected character '@'` |
| E1002 | Unterminated string | `unterminated string literal` (hint: strings must close on the same line) |
| E1003 | Invalid escape sequence | `invalid escape sequence '\q'` (hint: valid escapes are \n \t \" \\) |

**Syntax — `E2xxx` (phase “Syntax Error”)**

| Code | Meaning | Example message |
|---|---|---|
| E2001 | Unexpected token | `expected an expression, found ')'` |
| E2002 | Missing `;` | `expected ';' after statement` |
| E2003 | Unclosed delimiter | `expected '}' to close block opened at line 3` |
| E2004 | Invalid assignment target / form | `invalid assignment target` ; `assignment is a statement, not an expression` |
| E2005 | Task declared in a nested position | `tasks can only be declared at the top level` |
| E2006 | Nesting too deep | `program is nested too deeply (limit 200)` |
| E2007 | Missing parentheses around condition | `expected '(' after 'when'` |
| E2008 | Missing/invalid parameter or type annotation | `expected ':' and a type after parameter 'x'` |

**Semantic — `E3xxx` (phase “Semantic Error”)**

| Code | Meaning | Example message |
|---|---|---|
| E3001 | Undeclared name | `use of undeclared variable 'total'` |
| E3002 | Redeclaration / shadowing | `'x' is already declared at line 2` (hint: MiniLang does not allow shadowing) |
| E3003 | Type mismatch in initialization/assignment | `cannot assign string to variable 'age' of type int` |
| E3004 | Invalid operand types for operator | `cannot apply '+' to int and string` |
| E3005 | Condition is not bool | `condition must be bool, found int` |
| E3006 | Wrong number of arguments | `task 'add' expects 2 arguments, got 1` |
| E3007 | Call of a non-task name | `'x' is a variable, not a task` |
| E3008 | Argument type mismatch | `argument 2 of 'add' expects int, found string` |
| E3009 | Assignment to a global inside a task | `cannot assign to global variable 'count' inside a task` |
| E3010 | `give` outside a task | `'give' is only allowed inside a task` |
| E3011 | Return/give type mismatch | `task 'f' is declared to return int but this path returns string` ; `a void task cannot return a value` |
| E3012 | Missing give on some path | `task 'f' does not return a value on every path` |
| E3013 | Void value used as a value | `task 'greet' returns no value` |
| E3014 | Unknown type name | `unknown type 'integer'` (hint: valid types are int, float, string, bool) |
| E3015 | Reserved name used | `'int' is a reserved name` ; `names starting with '__nx_' are reserved` |
| E3016 | Duplicate task name or parameter | `task 'add' is already defined at line 1` |
| E3017 | `stop` outside a loop | `'stop' is only allowed inside a 'during' loop` |
| E3018 | `skip` outside a loop | `'skip' is only allowed inside a 'during' loop` |
| E3019 | Invalid type for `ask` | `'ask' does not support type 'bool'; valid types: int, float, string` |

**Warnings — `W4xxx` (phase “Warning”, severity `warning`)**

| Code | Meaning |
|---|---|
| W4001 | Unreachable code after `give` |
| W4002 | Division or modulo by constant zero (will fail at runtime) |
| W4003 | Variable declared but never used |

**Runtime — `R5xxx` (phase “Runtime Error”, produced by the runner)**

| Code | Meaning |
|---|---|
| R5001 | Division or modulo by zero |
| R5002 | Time limit exceeded (default 5 s) |
| R5003 | Recursion limit exceeded |
| R5004 | Output limit exceeded |
| R5005 | Other runtime failure of the generated program |
| R5006 | Invalid `ask` input (stdin could not be parsed as the declared type) |

Adding a code requires editing this table in the same PR (AGENTS.md §8.4).

### 3.5 Message style guide

1. State **what is wrong**, then **what was expected or found**. Prefer one sentence, lowercase start, no trailing period.
2. Quote names, tokens, and types with single quotes: `'total'`, `';'`.
3. Mention the declaring line when it helps: `'x' is already declared at line 2`.
4. Put advice in `hint`, not in `message`.
5. Never expose Python internals, tracebacks, or compiler class names.
6. Be consistent: “expected X, found Y”.

Good: `cannot apply '+' to int and string` with hint `convert explicitly or use two strings`.
Bad: `TypeError in BinaryExpr`.

### 3.6 Plain-text rendering (CLI)

```
error[E3001]: use of undeclared variable 'total'
  --> line 4, column 6
   |
 4 | show(total);
   |      ^^^^^
   = hint: declare it first with 'make total = ...;'
```

`render(diagnostic, source) -> str` produces this. Tabs in the excerpt are rendered as four spaces for alignment. Diagnostics are printed sorted by `(line, column)`; a summary line ends the output: `2 errors, 1 warning`.

### 3.7 JSON shape (API)

```json
{ "phase": "Semantic Error", "code": "E3004", "severity": "error",
  "message": "cannot apply '+' to int and string",
  "line": 3, "column": 15, "length": 1,
  "hint": "convert explicitly or use two strings" }
```

### 3.8 Recovery strategy per phase

#### 3.8.1 Lexer — fail fast (v1)

The lexer raises `LexerError` on the first invalid character/string. Rationale: after a lexical error the token stream is unreliable, and reporting parser errors derived from it would be noise. The pipeline returns that one diagnostic and stops.

*Future option (not v1):* emit an `ERROR` token and continue to report multiple lexical errors.

#### 3.8.2 Parser — panic-mode recovery

When the parser hits an error it records a diagnostic, then **synchronizes**:

1. Enter panic mode (suppress further diagnostics until synchronized, so one mistake yields one message).
2. Discard tokens until one of:
   - a `;` has just been consumed, or
   - the next token is a statement starter: `make when during task give show ask stop skip`, or
   - the next token is `}` (end of the current block), or
   - `EOF`.
3. Leave panic mode and continue parsing the next statement.

Additional rules:
- **Missing `;`:** if the next token begins a new statement on a later line, report E2002 at the end of the previous token and *continue without discarding* (it is the most common mistake and cheap to recover from).
- **Unclosed `{`:** report E2003 at EOF with a note of the opening line.
- A guard ensures the parser always consumes at least one token per recovery cycle (no infinite loops).
- The partial AST is discarded by the pipeline when any syntax error exists.

#### 3.8.3 Semantic analyzer — collect everything

- Report every error; never raise for user mistakes.
- A failed expression gets the special `ERROR` type, which is compatible with every other type. Operators and assignments involving `ERROR` produce **no further diagnostics** (prevents cascades: one undeclared variable should not generate five type errors).
- A name that fails to resolve is still declared, as `ERROR`-typed, after the first report when it appears in a `make` (so later uses don't repeat E3001 for a name the user clearly attempted to introduce).
- Stops at `DiagnosticBag.MAX_ERRORS`.

#### 3.8.4 Runner — runtime errors

The generated Python carries a **line map** (generated line → MiniLang line). When a run fails, the runner parses the Python traceback, maps the last frame back to a MiniLang line, and emits an `R5xxx` diagnostic. Users never see Python tracebacks.

### 3.9 Pipeline behaviour

| Condition | Result |
|---|---|
| Lexical error | `ok: false`, one E1xxx diagnostic, no later phases |
| ≥ 1 syntax error | `ok: false`, all E2xxx diagnostics, semantic analysis skipped |
| ≥ 1 semantic error | `ok: false`, all E3xxx (plus warnings), IR and later skipped |
| Warnings only | `ok: true`, continue |
| Runtime failure | `ok: true` for compilation; `run` contains the `R5xxx` diagnostic |

Compilation failure and runtime failure are different things: compiling is `ok` if the program is valid even when it divides by zero at runtime.

## 4. Alternatives considered

1. **Throw on the first error in every phase.** Simplest, but a poor user experience and a weaker project.
2. **Error productions in the grammar.** Powerful but complex; panic mode is enough for v1.
3. **Phrase-level recovery (insert/delete a single token).** More precise but easy to get wrong; reserved for a later improvement for the specific “missing `;`” case only.
4. **Free-form error strings without codes.** Rejected: tests and UI need stable identifiers.
5. **Localized messages.** Out of scope for v1; codes make future translation possible.

## 5. Drawbacks and risks

- Panic-mode recovery can still produce a misleading second error in rare cases; mitigated by suppressing errors until synchronized and by tests on common mistakes.
- Maintaining a code table requires discipline; enforced by the PR rule and a test that every emitted code exists in the table (a registry check).
- Line maps add work in the code generator (RFC-0008).

## 6. Impact on other components

- **`errors.py`:** replace the first-draft `NexoraError(message, line, column, phase)` with `Diagnostic`, `DiagnosticBag`, `NexoraError(diagnostic)`, and `InternalCompilerError`. Keep `LexerError(message, line, column)` constructors working by delegating to `Diagnostic` with the right code (`E1001` default). Update the lexer to pass explicit codes (`E1001`, `E1002`, `E1003`).
- **Parser:** uses the bag + synchronization (§3.8.2).
- **Semantic analyzer:** uses the bag and the `ERROR` type (RFC-0005).
- **Runner / codegen:** line map and R5xxx mapping (RFC-0008, RFC-0009).
- **Frontend:** renders the JSON shape (§3.7), underlines using `length`, links codes to docs.

## 7. Test plan

- One test per code: triggers it and asserts `code`, `line`, `column`, and message text.
- Rendering tests: golden strings for `render()` including tabs and end-of-file positions.
- Recovery tests: sources with two independent syntax errors yield two diagnostics; one mistake yields one diagnostic (no cascade).
- `ERROR`-type test: `make a = b + c;` with both undeclared yields exactly two E3001s and nothing else.
- Registry test: every code used in `nexora/` is present in this RFC's table (parsed from a `CODES` dict kept in `errors.py`).
- Limit test: 100 errors produce 50 diagnostics plus the “too many errors” note.
- Robustness (fuzz-style): random token sequences never hang or crash the parser; only diagnostics result.

## 8. Open questions

1. Should the lexer collect multiple errors in v1.1? (Proposed: yes if time allows, via an `ERROR` token.)
2. Should `W4003` (unused variable) be on by default? (Proposed: yes, as a warning.)
3. Do we show hints in the UI as a separate line or inline? (Frontend decision, RFC-0010.)
