# RFC-0007: Optimizer

- **Status:** Proposed
- **Author(s):** Nexora team
- **Created:** 2026-10-28
- **Depends on:** RFC-0001, RFC-0003, RFC-0005, RFC-0006
- **Supersedes / Superseded by:** — / —

## 1. Summary

This RFC defines Nexora's optimizer. It has **two levels** that share one set of folding rules:

1. an **AST-level optimizer** (constant folding, safe algebraic simplification, constant-branch and dead-code elimination) whose output feeds the Python code generator;
2. a **TAC-level optimizer** (local constant propagation, copy propagation, folding, branch folding, unreachable-code removal, jump cleanup, dead-code elimination) whose output is shown in the UI and is the foundation for future low-level targets.

Both levels MUST preserve observable behaviour exactly: the same output, in the same order, and the same runtime errors.

## 2. Motivation

The project brief lists optimization as a phase that “simplifies safe, supported expressions and removes unnecessary operations”. The risk with optimizers is not doing too little but doing something *wrong*: folding `1 / 0` into a compile-time crash, deleting a call that prints, or reordering evaluation. This RFC therefore defines the allowed transformations narrowly, states the safety rules precisely, and demands differential testing.

Splitting into two levels is a deliberate trade-off (RFC-0002 §3.3): the AST level keeps the generated Python readable (the user's variables and structure survive), while the TAC level demonstrates the classical IR optimizations.

## 3. Detailed design

### 3.1 Public API

```python
@dataclass(frozen=True)
class OptimizationNote:
    level: str          # "ast" | "tac"
    kind: str           # "fold", "simplify", "dead-branch", "dead-code", "propagate", "jump", ...
    line: int           # MiniLang line (0 if synthetic)
    column: int
    before: str         # short text of the old form, e.g. "3 * 4"
    after: str          # short text of the new form, e.g. "12"

@dataclass
class OptimizationReport:
    notes: list[OptimizationNote]
    iterations: int

def optimize_program(program: Program) -> tuple[Program, OptimizationReport]: ...
def optimize_tac(tac: list[TACInstr]) -> tuple[list[TACInstr], OptimizationReport]: ...
```

- `optimize_program` **never mutates its input.** It first clones the tree with `clone_tree(program)` (RFC-0003 addendum below), which copies nodes but *shares* annotation objects (`type`, `symbol`). The original annotated AST stays available for the UI.
- `optimize_tac` returns new instruction lists; input instructions are frozen.
- `options.optimize == False` skips both functions (the “O0” path used for differential tests).
- The pipeline records `before`/`after` texts using `unparse(expr)` (a MiniLang pretty-printer added to `ast_nodes.py`) and `format_tac`.

`ast_nodes.py` gains `NodeTransformer` (post-order rewrite; each `visit_X` returns the replacement node), `clone_tree`, and `unparse`.

### 3.2 Safety rules (non-negotiable)

An optimization is allowed only if it preserves **all** of the following.

1. **Output:** the sequence of `show` outputs.
2. **Runtime errors:** if the original program would raise a runtime error at some point (R5001 division by zero, R5003 recursion limit, overflow, …), the optimized program MUST raise the same error at the same logical point (after the same prior output). Therefore a computation that *can raise* is never folded or removed unless it is proved not to raise.
3. **Evaluation order and side effects:** calls and `show` are side-effecting. They are never removed (unless in provably unreachable code), duplicated, or reordered relative to each other or to anything that may raise.
4. **Types:** the type of every expression stays the same. A folded constant has the same MiniLang type as the expression it replaces (an `int / int` fold produces a `float`).
5. **Short-circuit:** a right operand that is never evaluated may be dropped; one that is evaluated must still be evaluated.

**Never-fold set.** Folding returns “no result” (and the node is left untouched) whenever evaluating the operation at compile time would:

- raise any `ArithmeticError` (`ZeroDivisionError` for `/ 0` and `% 0` with int or float zero, `OverflowError` for huge int→float conversion or division result too large);
- yield a non-finite float (`inf`, `nan`) — Python source has no literal for them and equality semantics are surprising;
- yield an int with more than 10,000 bits, or a string longer than 64 KB (compile-time blowup guard);
- involve any non-constant operand.

### 3.3 Shared folding module

`optimizer.py` exposes pure functions used by both levels so they cannot disagree:

```python
def fold_unary(op: str, value, vtype: Type) -> tuple[object, Type] | None
def fold_binary(op: str, left, ltype: Type, right, rtype: Type) -> tuple[object, Type] | None
```

Algorithm for `fold_binary`:

1. Compute the result type with `symbols.binary_result_type(op, ltype, rtype)` (RFC-0005 §3.2). If it returns `None`/`ERROR`, return `None`.
2. Evaluate with the **same Python operators the generated code will use** (`+ - * / % == != < <= > >=`, string `+`), inside `try/except ArithmeticError` → `None`.
3. Apply the never-fold checks of §3.2.
4. Check the Python result's type matches the expected MiniLang type (`bool`, `int`, `float`, `str`); otherwise return `None` (defensive).

Because the compile-time evaluator and the runtime both use Python's semantics, they agree by construction (e.g. `7 / 2 → 3.5`, `-7 % 3 → 2`, `1 == 1.0 → true`).

`both`/`either` on constants are handled by the short-circuit rules in §3.4, not by `fold_binary`.

### 3.4 AST-level optimization

Runs on a cloned tree to a **fixed point** (max 10 iterations; each iteration is one post-order rewrite). All rewrites keep the replaced node's `line`/`column` and copy its `type` annotation.

**A. Expression folding (post-order)**

| Pattern | Rewrite |
|---|---|
| `Unary(-, IntLiteral n)` / `FloatLiteral` | literal of `-n` |
| `Unary(not, BoolLiteral b)` | `BoolLiteral(not b)` |
| `Binary(op, Lit a, Lit b)` (both constants) | `fold_binary` result as a literal, if not “never-fold” |
| `yes both e` → `e`; `no both e` → `no` | right operand is not evaluated when left is `no`, so dropping it is safe |
| `yes either e` → `yes`; `no either e` → `e` | same reasoning |
| `e both yes` → `e`; `e either no` → `e` | `e` is still evaluated exactly once |

*Not* rewritten: `e both no`, `e either yes` (they would drop a possibly-raising or side-effecting `e`).

**B. Safe algebraic simplification** — only for **`int`-typed** operands, only identities that do not drop an evaluation:

| Pattern | Rewrite |
|---|---|
| `e + 0`, `0 + e`, `e - 0`, `e * 1`, `1 * e` (with `e : int`) | `e` |
| `not (not e)` | `e` |

Explicitly excluded: float identities (`x + 0.0` changes `-0.0`), `e * 0` (drops `e`, which may raise or call), `e / 1` (changes type to float), string identities.

**C. Statement-level rewrites**

| Pattern | Rewrite |
|---|---|
| `when (yes) A otherwise B` | `A` (as a `Block`) |
| `when (no) A otherwise B` | `B`; if no otherwise: remove the statement |
| `during (no) { … }` | remove the statement |
| statements after a `GiveStmt` in the same block | remove (they are unreachable; already warned as W4001) |
| `ExprStmt` of a literal or identifier | remove (no effect) |

`during (yes)` is left unchanged. Blocks are never merged across scopes in a way that changes names (RFC-0001 forbids shadowing, and Python has function scope, so inlining a `Block` into its parent is safe).

**D. What the AST level deliberately does not do**

- No constant *propagation* through variables. The user's `make` statements survive into the Python output, keeping it readable and debuggable. Propagation is shown at the TAC level.
- No inlining, loop optimizations, or reordering.

### 3.5 TAC-level optimization

Operates per function on the CFG from RFC-0006 §3.6 and runs to a fixed point (max 10 rounds). Order in each round:

1. **Local value propagation** (per basic block).
   - Maintain `env: operand → Const | Var | Temp`, empty at each block start.
   - On `Copy x = y`: after resolving `y` through `env`, record `env[x] = y` (if `y` is a `Const` or a name not equal to `x`).
   - On any instruction defining `d`: first drop `env[d]` and every entry whose value is `d` (kill), then record the new fact if the instruction is a copy.
   - Replace operands by their `env` values in `BinOp`, `UnOp`, `Copy`, `IfFalse`, `IfTrue`, `Param`, `Return`, `Print`.
   - Calls do not kill facts: a call cannot modify the caller's variables (RFC-0001 §3.4 rule 7).
2. **Folding.** `BinOp`/`UnOp` with all-`Const` operands → `Copy dest = Const` via §3.3.
3. **Algebraic simplification** — the same table as §3.4 B.
4. **Branch folding.** `IfFalse Const → goto/no-op`, `IfTrue Const → goto/no-op` according to the constant.
5. **Unreachable-block removal.** Rebuild the CFG; delete blocks not reachable from the entry. Removes the trailing provably-unreachable `return` of non-void functions and code after folded branches.
6. **Jump cleanup.**
   - `goto L` immediately followed by `L:` → delete the `goto`;
   - `goto L1` where `L1:` is immediately followed by `goto L2` → `goto L2` (thread jumps; guard against cycles with a visited set);
   - labels with no remaining references → delete.
7. **Dead-code elimination.**
   - Compute use counts: for temps and function locals/parameters per function; for **global** variables (those assigned in `__main`) over the **whole program by name** (a function that reads a global uses its name).
   - Delete an instruction whose destination has zero uses **and** which cannot raise or have side effects.
   - `may_raise(instr)`: `BinOp` `/` or `%` whose right operand is not a non-zero `Const`; `UnOp float` applied to a non-`Const` (huge int → `OverflowError`); `Call`. Side-effecting: `Call`, `Print`, `Return`, `Param`, jumps and labels.

**Example**

```
make a = 10;
make b = 20;
make r = a + b * 2;
show(r);
```

Unoptimized TAC (`__main`):

```
a = 10
b = 20
t1 = b * 2
t2 = a + t1
r = t2
print r
```

After round 1 (propagation + folding): `t1 = 40`, `t2 = 50`, `r = 50`, `print 50`. After dead-code elimination (nothing reads `t1`, `t2`, `r`, `a`, `b` any more):

```
print 50
```

The **AST-level** result for the same program leaves the Python as `a = 10`, `b = 20`, `r = a + b * 2` (only literal-only sub-expressions fold), keeping user variables visible.

**Counter-example (what must NOT happen)**

```
make z = 0;
make t = 5 / z;     // runtime error R5001 here
show(1);
```

`5 / z` is not folded at the AST level (`z` is a variable). At the TAC level propagation produces `t1 = 5 / 0`; `fold_binary` returns `None` (ZeroDivisionError), so the instruction stays. Dead-code elimination also keeps it, because `may_raise` is true even though `t1`'s result is unused. The program still fails with R5001 before printing `1`.

### 3.6 Idempotence and termination

- Each pass strictly decreases or leaves unchanged `(instruction count, number of non-literal operands)`; the round loop stops when a full round makes no change or after 10 rounds.
- Idempotence property: `optimize(optimize(x)) == optimize(x)`. Tested.
- Complexity: each round is linear in program size (one CFG build, one scan per pass); jump threading uses a visited set.

### 3.7 Interaction with warnings and diagnostics

Optimization runs only when the program has **no errors**. It does not remove or add diagnostics (warnings such as W4001/W4002 are produced by the semantic phase *before* optimization and remain visible). Runtime error line numbers refer to the **generated Python line map**, which is built from the optimized AST; folded nodes keep their original position, so errors still point to the right MiniLang line.

### 3.8 Reporting

`OptimizationReport.notes` powers the UI: “line 7: folded `3 * 4` → `12`”, “line 12: removed unreachable `otherwise` branch”. Notes are emitted in the order the transformations occurred and are capped at 500 per compilation (then a final “and N more” note).

## 4. Alternatives considered

1. **Only a TAC optimizer, and generate Python from optimized TAC.** Rejected: Python from TAC is unreadable (RFC-0002 §3.3).
2. **Only an AST optimizer.** Rejected: loses the classic IR-optimization demonstration (CFG, propagation, dead-code elimination).
3. **Global data-flow analysis (reaching definitions, liveness) at TAC level.** More powerful but larger. Local propagation plus whole-program use counts cover the demonstration needs; global analysis is a future RFC.
4. **Fold `e * 0` → `0`, `e both no` → `no`.** Rejected: changes behaviour when `e` raises or has side effects, unless a purity analysis is added.
5. **Compile-time evaluation of pure task calls.** Out of scope for v1.
6. **Use Python's `ast.literal_eval`/`eval` for folding.** Rejected on security grounds (rules.md §11) and because it would not respect MiniLang's type rules.

## 5. Drawbacks and risks

- Two optimizers mean more code and more tests. Shared `fold_*` functions and differential tests limit the risk.
- “Never fold” cases leave some obviously constant expressions untouched (e.g. a folded float that would overflow). That is the price of exact behaviour preservation.
- Optimized TAC is not used for Python generation in v1, so the TAC optimizer is currently *demonstrative*. The UI must say so (“TAC optimization is shown for study; generated Python comes from the optimized AST”).

## 6. Impact on other components

- **`ast_nodes.py`:** adds `NodeTransformer`, `clone_tree`, `unparse` (small, additive to RFC-0003).
- **`symbols.py`:** must export `binary_result_type` and `unary_result_type` used by both semantic analysis and folding.
- **Pipeline:** `optimize_program` between semantic analysis and code generation; `optimize_tac` after IR generation; reports returned in `CompileResult.optimization`.
- **Frontend:** optimization notes panel; before/after TAC diff.
- **Runner:** unaffected (it just runs the generated code).

## 7. Test plan

- **Fold table:** one test per operator and type combination, including `7 / 2`, `-7 % 3`, `1 == 1.0`, string concat and comparison, bool logic.
- **Never-fold tests:** `1 / 0`, `1.0 / 0.0`, `5 % 0`, huge int to float (a 400-digit integer literal divided by `1`), results over the size limits — all remain unchanged.
- **Short-circuit tests:** each row of §3.4 A, plus the “not rewritten” rows.
- **Identity tests:** int-only; float and string variants unchanged.
- **Statement rewrites:** constant `when`/`otherwise when` chains, `during (no)`, dead code after `give`.
- **TAC pass tests:** propagation across kills, copy chains, block boundaries (no propagation across labels), branch folding, jump threading including a cycle, unused-label removal, dead-code rules for may-raise instructions, global use-count rule.
- **Differential tests (most important):**
  1. For every example and fixture: `run(compile(optimize=False)) == run(compile(optimize=True))` (stdout, runtime error code, error line).
  2. `tac_vm(tac) == tac_vm(optimized_tac)`.
- **Property tests:** a seeded random generator of small well-typed programs (int/float/bool expressions, `when`, `during` with bounded counters, calls) checks both differential properties on 500 programs per CI run (`random.Random(seed)`; `hypothesis` is an allowed dev dependency if the team prefers).
- **Idempotence test** and **non-mutation test** (the input `Program` compares equal before and after `optimize_program`).
- **Validator:** `validate_tac` runs after every TAC pass in tests.

## 8. Open questions

1. Should `-O0`/`-O1` levels be exposed in the CLI/API? (Proposed: boolean only in v1.)
2. Should unused variable stores at the AST level be removed? (Proposed: no; it would change what the user sees in the generated Python.)
3. Should the optimizer reuse W4002 (“division by constant zero”) to annotate TAC? (Proposed: no.)
